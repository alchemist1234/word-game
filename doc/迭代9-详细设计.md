### 2.1 核心决策

- **前端平台层只做“适配”不做“业务”**：`pages/*` 与 `store/game.ts` 仅调 `platform/auth` 与 `platform/request`，不含 `#ifdef`。条件编译收敛在 `platform/` 内，便于新增/下线一端时只改 `platform/` + `manifest.json`。
- **请求层强制 uni.request**：H5 亦走 `uni.request`（uni-app H5 对 `uni.request` 已做 `XMLHttpRequest` 封装，行为与小程序一致），消除 `fetch` 仅 H5 的分叉；WS 仍 `uni.connectSocket`，地址由 `env.ts` 注入。
- **后端 mock 优先**：抖音/快应用/TapTap 登录均 **mock：code 即 openid**，与现有 `wechat_mp` 一致；真实 `code2session`（微信 `jscode2session`、抖音 `jscode2session`、快应用 `getAuthCode`）在 `PlatformService` 占位 `realVerify(code)` 方法，迭代 10 替换。
- **TapTap 视为渠道而非独立编译目标**：编译产物与 Android App 一致（`APP-PLUS`），运行时通过 `plus.runtime` 或启动参数识别渠道，`platform` 传 `taptap` 即可落库区分。
- **App WS 基址注入**：`VITE_API_BASE`（如 `https://api.example.com` 或 `http://192.168.x.x:3000`）在 `vite.config.ts` 的 `define` 或 `.env` 注入，`env.ts` 优先读 `import.meta.env.VITE_API_BASE`，H5 兜底 `location.host`。

### 4.4 `request.ts`（统一 `uni.request`）

> 偿还技术债 #12：`client/src/api/index.ts` 的 `fetch` 全量替换。

```typescript
import { getToken, clearToken } from './storage'

interface RequestOptions { method?: string; data?: unknown; header?: Record<string, string> }
export function request<T>(url: string, opts: RequestOptions = {}): Promise<T> {
  const token = getToken()
  const header: Record<string,string> = { 'Content-Type': 'application/json', ...(opts.header||{}) }
  if (token) header['Authorization'] = `Bearer ${token}`
  const base = getApiBase() // '' 或 VITE_API_BASE
  return new Promise<T>((resolve, reject) => {
    uni.request({
      url: `${base}/api${url}`, // 统一 /api 前缀（H5 代理，小程序/App 直连）
      method: (opts.method || 'GET') as any,
      data: opts.data as any,
      header,
      success: (res) => {
        if (res.statusCode === 401) { clearToken(); uni.reLaunch({ url: '/pages/Login/index' }); reject(new Error('未授权')) ; return }
        if (res.statusCode >= 200 && res.statusCode < 300) resolve(res.data as T)
        else reject(new Error((res.data as any)?.message || `请求失败 ${res.statusCode}`))
      },
      fail: (err) => reject(new Error(err.errMsg || '网络错误')),
    })
  })
}
```

- `api/index.ts` 所有 `fetch` 调点改为 `request<T>('/auth/login', { method:'POST', data:{...}})` 形式；`RequestInit/Response` 类型移除；错误透传 `message`。
- **兼容**：`uni.request` 在 H5 端已可用（uni-app H5 封装），无需保留 `fetch` 分支；若担心 H5 调试可用 `#ifdef H5` 回退 `fetch`，但首选统一。
- **超时**：`uni.request` 默认 60s，`request` 中可加 `timeout: 15000`（可选）。

### 6.3 `AuthService` 重构（手机号主键合并，核心）

**现状**：`loginOrCreate(platform,openid)` 仅按 `(platform,openid)` 查找，不合并。

**目标**：同手机号 ⇒ 同 `user.id`；流程如下（用户已确认）：

```
POST /auth/login { platform, phone?, code }
  |
  ├─ phone+code（手机号登录，platform 任意含 h5/app/taptap/wechat_mp 等）：
  │   1. 校验 code === '1234'（mock）
  │   2. openid = phone（手机号平台 openid 取 phone，统一）
  │   3. 若 user_auths(platform,openid) 已存在 → 直接签 JWT
  │   4. 否则查 users(phone)：
  │       - 存在 → 复用该 user，新建 user_auths(platform,openid,userId) 绑定
  │       - 不存在 → 新建 user(phone) + user_auths
  │
  ├─ code（小程序/快应用/App 微信登录，platform=wechat_mp/douyin_mp/quickapp/app/taptap）：
  │   1. openid = PlatformService.normalizeOpenId(platform, code)（=code）
  │   2. 查 user_auths(platform,openid) → 存在则签 JWT
  │   3. 不存在 → 新建匿名 user(phone=null) + user_auths（不合并，待绑定）
  │   4. 前端收到 匿名 user 后引导“绑定手机号”（调 bind-phone）
  │
  └─ JWT payload 保持 { userId, platform }，JWT 校验与现有 JwtAuthGuard 一致（Number(payload.userId)）

POST /auth/bind-phone { phone, code }  (需 JWT)
  1. 校验 code === '1234'
  2. 若 phone 已被其他 user 占用：
      - phone 对应 oldUser 与当前 user 为同一人 → 幂等返回
      - 否则 **合并**：把当前 user 的所有 user_auths 迁移到 oldUser（update auth.userId=oldUser.id），将当前 user 的进度/成就/图鉴/经济择需合并（首版：仅迁移 auth，进度保留 oldUser 为准；当前 user 标记废弃或保留不删）
      - 合并后签新 JWT（userId=oldUser.id）
  3. 否则（phone 未被占用）→ 更新当前 user.phone=phone，补建/更新 wechat_mp 等平台的 openid=phone 绑定（可选），签新 JWT
  4. 返回 { token, user }
```

> **合并细节（首版简化，可验证）**：
> - 行级锁：`SELECT ... FOR UPDATE` 或事务内先查后写（单实例可接受先查后写，乐观重试）。
> - `users.phone` 唯一约束：并发绑定同手机号时一个成功、一个 `QueryFailedError` 412，需 catch 转 `409 PHONE_BOUND`。
> - 旧匿名 user 的 `found_words/chapter_progress/economy` 首版**不自动合并**（避免复杂冲突），以手机号归属的已存在 user 为准；旧 user 的 `user_auths` 已迁移，新请求即走 oldUser，后续请求自然落地。文档中登记此简化（§15）。
> - 合并后旧 `users` 行可保留（标记 `mergedTo=oldUser.id` 可选字段，首版不新增字段，仅迁移 auth）。

### 8.1 流程图

## 17. 需要注意的坑（对齐前几轮联调经验）

1. **`uni.request` header 大小写**：部分小程序对 `Authorization` 大小写敏感，保持首字母大写 `Authorization: Bearer`，`uni.request` 的 `header` 同理。
2. **抖音 `tt` 全局**：`mp-toutiao` 下 `tt` 可能未在类型中声明，`auth.ts` 中 `declare const tt: any` 或 `// @ts-ignore` 隔离，且用 `uni.login` 优先（抖音对 `uni.login` 已兼容）。
3. **快应用 `userId` 类型**：`JwtAuthGuard` 已统一 `Number(payload.userId)`（迭代 6 §14.5 修复），快应用登录同样走此分支，避免 Map key 仍为字符串 `"3"`。
4. **`VITE_API_BASE` 末尾斜杠**：`getApiBase()` 必须 `replace(/\/+$/,'')`，否则 `url = base + /api/...` 双斜杠；`getWsBase` 的 `http→ws` 替换需同时处理 `https→wss`。
5. **App 局域网联调**：手机与电脑同 WiFi，`VITE_API_BASE=http://192.168.x.x:3000`，且防火墙放行 3000 端口；`vite --host` 已在 H5 代理态，App 直连不走 Vite。
6. **HBuilderX 云打包**：`client/` 需为 HBuilderX 项目根（含 `manifest.json`/`pages.json`），`appid` 为空时云打包仍可出测试包；`app-plus` 的 `permissions` 缺失会导致 App 网络请求被拦截。
7. **`bindPhone` 并发**：两端同时绑定同手机号时一个 `UNIQUE` 冲突 → `409 PHONE_BOUND`，前端应提示“该手机号已被绑定，请直接用手机号登录”。
8. **Storage 同步**：`uni.getStorageSync` 在部分小程序首次读 `token` 可能为 `undefined`，`storage.ts` 的 `|| ''` 兜底不可省。
9. **`synchronize:true` 与 `platform` 枚举**：PG 不对 `platform` 做 CHECK 约束，仅靠 `@IsIn` 校验；脏数据可 `SELECT DISTINCT platform FROM user_auths` 排查。
10. **TapTap 渠道识别**：`uni.getSystemInfoSync` 在 App 上不含渠道，需靠 `uni.getStorageSync('channel')` 或打包时写入 `client/src/platform/channel.json`，勿依赖 `plus.runtime.appid`。
11. **`build:mp-toutiao` 与 `build:mp-weixin` 产物隔离**：`dist/build/mp-toutiao` 与 `dist/build/mp-weixin` 分目录，CI 需分别 `npm run build:mp-weixin && npm run build:mp-toutiao`，避免并发写同一 `dist`。
