## 1. 概述

### 1.1 背景与目标

对局中玩家连出一个自己认为是词的组合，系统判非法（`not_in_dict`）无任何出口，体验差且词库失去众包纠错机会。本迭代增加**用户反馈收词**闭环：

1. **对局内一键申请**：提词因“词库无此词”失败时，就近出现“申请收录”入口，预填词与路径证据，一次确认即提交。
2. **结算页申请**：对局结束后集中展示本局未收录词，可逐个申请；支持手动输入补报。
3. **我的申请**：可查自己申请过的词、当前状态与支持人数。
4. **众审自动入库**：同一词的不同用户申请数达到阈值（默认 **10 个不同用户**，一人反复提交只算 1 票）后，自动写入词库并即时生效（新开对局可用）。
5. **管理端预留**：暂无管理端，后续添加；表结构预留 `approved / rejected` 状态与审核字段，本迭代只实现 `pending → auto_merged` 自动路径。

### 1.2 非目标（Out）

- 管理端审核页与审核接口（→ 后续迭代，只预留状态与字段）。
- 敏感词/广告/灌水语义过滤系统（→ 后续；本迭代仅做格式校验 + 频次上限 + 高阈值，风险见 §11）。
- 已入库词的释义（`meaning`）自动生成：自动入库 `meaning=null`，与现有一致（导入脚本 `meaning` 本就为空，`server/src/scripts/import-dict.ts:81`）。
- 历史对局补分：申请通过前用该词的对局**不补分**（见决策 #4）。
- 对战（1v1/4人）对局内即时申请：为防干扰竞技节奏，对战中不出现申请入口，仅结算页可申请（见决策 #3）。

### 1.3 已确认决策

| # | 事项 | 决策 |
|---|---|---|
| 1 | 计数口径 | 按 `(word, userId)` 去重计数，一人反复提交只算 1 票（`UNIQUE(word, userId)`） |
| 2 | 自动入库阈值 | 默认 **10 个不同用户**，走配置 `WORD_APPLY_AUTO_MERGE_THRESHOLD`（环境变量覆盖），便于运营调参 |
| 3 | 对战中 | 对局进行中不打断，仅结算页可申请；单人/每日/好友对局内失败处可一键申请 |
| 4 | 历史对局 | 不补分不改结算；新词只对**新开会话**生效（会话持潜在词池快照，见 §2） |
| 5 | 自动入库稀有度 | 默认 `normal`（×1.3），`frequency` 取低值，不给 `rare/idiom` 高分，防止刷分套利 |
| 6 | 审核预留 | 状态机含 `approved/rejected`，本迭代不实现审核动作，只实现 `pending → auto_merged` |

## 2. 现状分析（证据）

- 提词判定 `server/src/game/game.service.ts:188-193`：`potentialMap.get(word)` 缺失即 `{ valid:false, reason:'not_in_dict' }`，非法词**不落库**，无任何记录。
- 客户端失败处理 `client/src/store/game.ts:402-406`（`handleWordResult`）与 HTTP 兜底分支：`fail` 仅置 `lastFeedback`，`pending` 出队即丢弃，词本身丢失——申请入口首先要**把本局 `not_in_dict` 的词留下来**。
- 词库内存化 `server/src/dictionary/dictionary.service.ts:29-50`：`loadAll()` 启动加载一次后常驻 `Map + Trie`，**无热刷新**——自动入库必须新增 `refresh()` 原子替换，否则入库后新对局仍不可用。
- 会话快照语义：`createSessionFromRaw`（`server/src/game/game.service.ts:59`）把 `potentialWords / potentialWordsWithRarity` 写进 `match_session`，`submitWord / endGame` 只认快照——已开对局不受词库变化影响，新词天然只对新会话生效，无需迁移。
- 词库约束（`server/src/scripts/import-dict.ts:32-34`）：2-6 字纯中文 `^[\u4e00-\u9fff]+$`；稀有度规则 `import-dict.ts:60-74`（成语 `idiom`，其余按词频三档）。用户申请词沿用同一格式门槛。
- `AppModule`（`server/src/app.module.ts:37`）`synchronize:true`，新增 entity 自动建表，与既有模块一致。
- 现无反馈/申请类表与接口（`server/src` 内无 `suggest/feedback/apply` 实现，已 grep 确认）。

## 3. 总体流程

### 3.1 用户旅程 A：对局内一键申请（单人/每日/好友）

```
提词失败（reason=not_in_dict）
  → 失败反馈区出现「“XX”词库暂无收录［申请收录］」
  → tap → 二次确认框（词 + 说明“需 N 位玩家申请才入库，本局不加分”）
  → POST /word-applies → Toast「已提交（已有 M 人申请，满 N 人自动入库）」
```

- 仅 `not_in_dict` 显示；`duplicate / path_invalid / word_not_match` 不显示（不是词库问题）。
- 对战 `matchMode / battle4pMode` 下不显示（决策 #3）。

### 3.2 用户旅程 B：结算页集中申请

```
结算页新增卡片「本局未收录的词」
  → 列出本局 not_in_dict 去重词（store.invalidAttempts）
  → 每行［申请收录］→ 结果态（已申请·M/N / 已入库）
  → 手动输入行（2-6字中文）+［提交］
```

### 3.3 用户旅程 C：我的申请

```
个人中心/结算页入口 → pages/WordApply/index
  → 列表：词 / 状态（审核中·M/N / 已入库 / 已驳回预留）/ 申请时间
```

### 3.4 系统旅程 D：众审自动入库

```
POST /word-applies（新去重票）
  → COUNT(DISTINCT userId WHERE word AND status IN (pending))
  → >= N 且词仍不在库 → 事务：dictionary INSERT + word_applies 全量置 auto_merged
  → dictionaryService.refresh()（Map+Trie 原子替换）
  → 返回 { autoMerged:true }，前端提示「已加入词库，新开对局可用」
```

### 3.5 系统旅程 E：后续人工审核（本迭代不做，预留）

```
管理端（后续）：GET 列表 / POST {approve|reject}
  → approve：等同自动入库写入；reject：置 rejected（若已 auto_merged 则同步从 dictionary 删除 + refresh）
```

## 4. 数据模型（PostgreSQL，`synchronize:true`）

### 4.1 `word_applies`（新增）

```typescript
@Entity('word_applies')
@Index(['word'])
@Index(['userId'])
@Index(['word', 'userId'], { unique: true }) // 一人一票
export class WordApplyEntity {
  @PrimaryGeneratedColumn() id!: number
  @Column({ type: 'varchar', length: 16 }) word!: string
  @Column({ type: 'bigint', name: 'user_id' }) userId!: number
  @Column({ type: 'varchar', length: 16, default: 'pending' })
  status!: string // pending | auto_merged | approved | rejected（后两者本迭代只预留）
  @Column({ type: 'varchar', length: 16, default: 'game' })
  source!: string // game（带路径证据）| manual（结算页手输）
  @Column({ type: 'varchar', length: 64, nullable: true, name: 'match_session_id' })
  matchSessionId!: string | null
  @Column({ type: 'jsonb', nullable: true })
  cells!: Array<{ row: number; col: number }> | null // 路径证据（game 来源）
  @Column({ type: 'varchar', length: 64, nullable: true, name: 'grid_seed' })
  gridSeed!: string | null // 会话 gridUuid 快照，备查
  @CreateDateColumn({ name: 'created_at' }) createdAt!: Date
  @UpdateDateColumn({ name: 'updated_at' }) updatedAt!: Date
}
```

- 去重键 `(word, userId)` 唯一：重复提交走更新时间戳，不增加票数。
- 查票数：`COUNT(*) WHERE word=? AND status IN ('pending')`（`auto_merged` 后不再计；`approved/rejected` 预留后同样排除）。
- `GET /word-applies/mine` 的每词支持数用 `GROUP BY word` 一次查出，避免 N+1。

### 4.2 `dictionary` 写入映射（自动入库时）

| 字段 | 取值 | 说明 |
|---|---|---|
| `word` | 原词 | 主键，去重（入库前再查一次防并发重复） |
| `length` | `word.length` | |
| `frequency` | `0.02` | 低值标记众包来源；展示用，不参与稀有度判定 |
| `rarity` | `'normal'` | 决策 #5：未知词频不高估，防刷分 |
| `tags` | `['player-suggest']` | 众包标记，便于运营筛选复核 |
| `chars` | `word.split('')` | |
| `meaning` | `null` | 与现有一致 |

### 5.1 新模块 `WordApplyModule`

server/src/word-apply/

- 依赖说明：校验路径证据需读 Redis 会话。会话读写统一在 `GameService`，为避免循环依赖，`WordApplyModule` **不导入** `GameModule`，改为经 `REDIS_TOKEN` 直读 `match_session:{sid}`（只读 `grid / gridUuid / userId` 三个字段）+ 复用 `validatePath` 纯函数（`server/src/game/check.ts`，无依赖可直接 import）。
- `DictionaryService` 需新增 `refresh()`（见 §5.4），`WordApplyService` 注入 `DictionaryService`（`DictionaryModule` 已 `exports`，见 `dictionary.module.ts:9`）。

### 5.2 接口（全部 JWT，与既有风格一致）

#### `POST /word-applies`（核心）

body：`{ word: string; matchSessionId?: string; cells?: Array<{row:number;col:number}> }`

处理顺序：

1. 归一化：`word.trim()`；校验 `^[\u4e00-\u9fff]{2,6}$`，不通过 → `400 WORD_INVALID`。
2. 查库 `dictionaryService.findByWord(word)`：已在库 → `200 { applied:false, inDict:true }`（前端提示“已收录，新开对局可用”，不计数）。
3. 证据校验（`matchSessionId` 有值时）：
   - `hgetall match_session:{sid}` 存在、`session.userId == req.user.userId`，否则 `404/403`；
   - `validatePath(cells)` 通过、路径拼字 `gridChars === word`，否则 `400 EVIDENCE_INVALID`；
   - 记录 `gridSeed=session.gridUuid`、`cells` 入库备查。
   - 无 `matchSessionId` 时记 `source='manual'`，跳过本步。
4. 当日上限：`COUNT(userId AND created_at >= 今日0点)`，`>=5` → `400 DAILY_LIMIT`（防刷）。
5. 幂等写入：`findOne({word, userId})` 存在则 touch `updatedAt` 返回；否则 `create(status='pending')`。
6. 计票：`COUNT(word WHERE status='pending')` → `supporters`。
7. 自动合并判定：`supporters >= threshold` → 走 §5.3（返回 `autoMerged:true`）。

返回：`{ applied:boolean; inDict?:boolean; supporters:number; threshold:number; status:string; autoMerged:boolean }`

#### `GET /word-applies/mine`

返回本人申请：`{ list: [{ word, status, supporters, createdAt }] }`（`supporters` 用一次 `GROUP BY` 补齐）。

#### `GET /word-applies/supporters?word=XX`

返回 `{ word, supporters, threshold, inDict, appliedByMe }`，供申请按钮旁“已有 M/N 人申请”展示与去重态判断。

### 5.3 自动合并（事务 + 幂等）

```typescript
// 伪逻辑（TypeORM 事务内）
if (supporters >= threshold) {
  const exists = await dictRepo.findOne({ where: { word } })
  if (!exists) {
    await dictRepo.save({ word, length, frequency: 0.02, rarity: 'normal',
      tags: ['player-suggest'], chars: word.split(''), meaning: null })
  }
  await applyRepo.update({ word }, { status: 'auto_merged' })
  await dictionaryService.refresh()
}
```

- 并发：两票同时达阈值时靠 `dictionary.word` 主键去重兜底（第二个 `save` 冲突则视为已入库，继续置状态 + `refresh`，不抛错）。
- 生效范围：仅新会话（快照语义，§2）；`grid_pool` 预生成网格不受影响（其潜在词池是生成时快照）；`lb:all`、成就、结算均不回写（决策 #4）。

### 5.4 `DictionaryService.refresh()`（新增，必须）

```typescript
async refresh(): Promise<void> {
  const entities = await this.repo.find()
  const trie = new Trie(); const cache = new Map()
  for (...) { trie.insert(...); cache.set(...) }
  this.words = words; this.trie = trie; this.cache = cache // 原子替换引用
}
```

- 现状 `loadAll()` 有缓存短路（`dictionary.service.ts:30`），`refresh` 绕过短路全量重建后整体替换，避免半更新。
- 单实例可直接调用；多实例部署时各实例内存不一致——登记技术债（见 §10），后续加发布订阅或重启任务。

## 7. 状态机

```
pending ──(达阈值)──▶ auto_merged
pending ──(后续管理端)──▶ approved | rejected   // 预留，本迭代不实现
auto_merged ──(后续管理端驳回)──▶ rejected + dictionary 删除 + refresh // 预留
```

- 本迭代只会产生 `pending` 与 `auto_merged`；`approved/rejected` 为字段与文档预留，前端状态文案需兼容未知状态回退显示原文。

## 11. 风险与说明（必读）

1. **无审核自动入库的内容风险**：阈值只能防数量，不能防质量（低俗/广告/引战词凑够人数即可入库）。缓解：默认阈值 10 不宜再低；`rarity=normal` 限分；`tags=['player-suggest']` 便于运营批量复核；`word_applies` 保留证据（`gridSeed/cells/source`）可追溯；**上线前建议先观察申请分布再决定是否降阈值**，敏感词表列为后续必做（Out）。
2. **多实例内存不一致**：`refresh()` 只刷新本实例；多副本需后续加 Redis pub/sub 或滚动重启。当前单实例可接受。
3. **证据有效期**：`match_session` TTL 600s，结算页申请需在有效期内提交；过期走 `source=manual`（无路径证据，照样计数，阈值兜底）。
4. **阈值与冷启动**：用户量小时 10 人难凑，属预期（宁缺毋滥）；后续管理端上线后可人工 `approved` 补位。
