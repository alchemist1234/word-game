> 平台：多端（微信/支付宝/抖音/百度/QQ/快手小程序 + 快应用 + H5 + Android/iOS App）

## 1. 游戏概述

### 1.1 一句话定位
一款基于汉字网格的**实时连线组词**休闲竞技小游戏：在 n×n 的汉字矩阵中，通过连接相邻汉字组成中文词语，按词长与稀有度积分，支持单人闯关与多人实时竞赛。

### 1.2 核心体验关键词
- **瞬时灵感**：汉字在网格中"忽然成词"的灵光一闪
- **稀有追求**：成语 / 生僻词带来的高分爆点
- **快节奏对抗**：3 分钟一局的紧凑对决
- **文化厚度**：成语、古诗、典故主题包带来的"识词成就感"

### 1.3 目标用户
| 用户画像 | 占比预估 | 核心诉求 |
|---|---|---|
| 通勤碎片时间玩家 | 50% | 单局短、上手快、有成就感 |
| 语文/文化爱好者 | 25% | 成语收集、主题关卡、词库图鉴 |
| 社交竞技型玩家 | 15% | 好友 PK、段位排行 |
| 学生/家长群体 | 10% | 寓教于乐、词汇积累 |

### 1.4 设计目标
1. **3 分钟上手**：首次进入 30 秒内能完成第一局有效操作
2. **每局都有"哇"时刻**：通过网格生成算法保证每局至少 1 个高分成语可形成
3. **社交裂变**：好友对战 + 每日挑战分享卡片，驱动拉新
4. **文化沉淀**：词库图鉴让"玩过即学过"

## 2. 核心玩法机制

### 2.1 网格与汉字

| 难度档 | 网格大小 | 字数 | 适用场景 |
|---|---|---|---|
| 入门 | 4×4 | 16 | 新手教学、休闲模式 |
| 标准 | 5×5 | 25 | 单人闯关主玩法、1v1 对战 |
| 高难 | 6×6 | 36 | 大师段位、限时挑战 |

- 每个格子放置**单个汉字**（不含标点、不含多字复合符号）
- 同一汉字可在网格中重复出现（增加偶然成词机会）
- 网格由**服务端生成**，客户端仅负责渲染与交互

### 2.2 连接规则

采用 Boggle 式连线，规则如下：

1. **8 方向相邻**：上、下、左、右、四个对角线，共 8 个方向
2. **不可重复使用**同一格子（一条词内每个格子最多经过一次）
3. **最短 2 字**，最长不超过网格总字数
4. 连线**有方向**（从首字到末字），顺序必须构成合法词语
5. 玩家手指/鼠标按下首字后**滑动经过**相邻字，松开提交

> 设计取舍：选 8 向而非 4 向。中文组词对相邻性更敏感（4 向会大幅减少可成词数，导致挫败感）。8 向是"易上手"的关键。

> **不支持跳跃连线**：严格相邻，不引入"跨越空格"档位。跳跃会破坏网格的空间逻辑性，且大幅增加判定复杂度，收益不明确。

### 2.3 词语判定

- 提交后由**服务端校验**是否在词库中（防作弊 + 统一判据）
- 词库分级（见 §3.1），不同级别计入不同稀有度
- **同一词一局只计一次**（重复找到不加分，但可触发"已找到"提示）
- 非法词（乱序、不在词库）给轻量负反馈（震动 + 红色描边 0.3s），不扣分

### 2.4 计分系统

计分由三部分组成：**字数基础分 × 稀有度系数 × 时效连击系数**。

#### 2.4.1 字数基础分

| 词长 | 基础分 | 示例 |
|---|---|---|
| 2 字 | 2 | "中国"、"朋友" |
| 3 字 | 5 | "自来水"、"说明书" |
| 4 字 | 10 | "春暖花开"、"画蛇添足" |
| 5 字 | 20 | "欲速则不达" |
| 6 字+ | 35 | "迅雷不及掩耳" |

> 设计意图：词长曲线陡峭，鼓励玩家寻找长词与成语，而非堆砌 2 字词。

#### 2.4.2 稀有度系数

| 稀有度 | 系数 | 判定依据 | 示例 |
|---|---|---|---|
| 常见 | ×1.0 | 词频 Top 30% | "我们"、"今天" |
| 一般 | ×1.3 | 词频 30%-60% | "犹豫"、"璀璨" |
| 罕见 | ×1.8 | 词频 60%-90% | "氤氲"、"倥偬" |
| 成语/生僻 | ×2.5 | 成语词典收录 / 词频后 10% | "守望相助"、"龃龉" |

词频数据来源：基于现代汉语语料库词频表（如《现代汉语常用词表》+ 网络语料统计），存于服务端词库集合。

#### 2.4.3 时效连击系数

- 玩家找到上一个词后 **10 秒内**找到下一个词，连击数 +1
- 连击系数 = `1 + 0.1 × min(连击数, 10)`（封顶 ×2.0）
- 超时则连击数清零
- **目的**：奖励"持续输出"，制造紧张感与爽快感

#### 2.4.4 计分示例

| 找到的词 | 基础分 | 稀有度 | 连击 | 得分 |
|---|---|---|---|---|
| 朋友（2字常见） | 2 | ×1.0 | ×1.0 | 2 |
| 犹豫（2字一般） | 2 | ×1.3 | ×1.1（连击1） | 2.86 ≈ 3 |
| 春暖花开（4字成语） | 10 | ×2.5 | ×1.2（连击2） | 30 |
| 守望相助（4字成语） | 10 | ×2.5 | ×1.3（连击3） | 32.5 ≈ 33 |

总分取整累加。一局标准 5×5 对战典型分数区间：**80 - 400 分**。

### 2.5 单局流程

```
进入对局 → 倒计时 3-2-1 → 网格揭示 → 3 分钟计时
   → 玩家连线组词（实时计分、连击提示）
   → 时间到 / 主动结束
   → 结算页（总分、找到的词列表、稀有词高亮、对手对比）
   → 返回大厅 / 再来一局 / 分享
```

## 3. 词库与网格生成

> 这是本游戏**最核心的技术与设计难点**。中文不像英文字母，汉字组词对字的组合高度敏感，网格必须保证"可玩性"——既不能太空（找不到词，挫败），也不能太满（满屏都是词，无挑战）。

### 3.1 词库设计

#### 3.1.1 词库结构

每条词记录字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `word` | string | 词语本体，如"春暖花开" |
| `length` | int | 字数 |
| `frequency` | float | 词频（0-1，归一化） |
| `rarity` | enum | common / normal / rare / idiom |
| `tags` | array | 主题标签：["成语","春天","景物"] |
| `chars` | array | 拆字数组，用于网格生成索引 |

#### 3.1.2 词库来源与规模

| 词库子集 | 规模（目标） | 来源 |
|---|---|---|
| 2字常用词 | 8,000 | 《现代汉语常用词表》（教育部公开数据）+ 语料库词频统计 |
| 3字词 | 3,000 | 同上 + 人工筛选 |
| 4字成语 | 8,000 | 开源成语库（如 GitHub 公开成语数据集 / CC-CEDICT 衍生） |
| 5-6 字俗语/典故 | 1,500 | 公开语料 + 人工筛选 |
| 主题包（古诗、节日、节气等） | 每包 500-1000 | 古诗：公开诗词数据集；节日节气：公共知识，运营整理 |

> 全部使用公开数据源，无商业授权依赖。词频数据基于公开现代汉语语料统计。

**总词库目标：2 万 + 条**，按主题与难度切片索引。

#### 3.1.3 稀有度自动标注

```
rarity =
  idiom      if 成语词典收录
  rare       if frequency < 0.10
  normal     if 0.10 <= frequency < 0.40
  common     if frequency >= 0.40
```

### 3.2 网格生成算法

#### 3.2.1 设计目标

- **可解性**：服务端预生成的"目标词集"中每个词在网格中至少存在一条合法路径
- **丰度可控**：难度参数控制目标词数量与稀有度分布
- **惊喜性**：网格中除了目标词，还应有机会形成大量"非目标但合法"的词（玩家偶然发现，爽点）
- **公平性**：对战模式双方收到**完全相同**的网格

#### 3.2.2 生成流程（服务端）

```
输入：grid_size, difficulty(level 1-10), theme(optional)

1. 根据难度从词库选取「目标词集」W：
   - level 越高，目标词越多、稀有词占比越高、成语占比越高
   - 例：标准难度目标词 = 3 个 2字常见 + 2 个 3字一般 + 2 个 4字成语

2. 收集 W 中所有字的并集 S = ∪ chars(W)
   - 若 |S| > 格子数：剔除部分目标词或允许字复用
   - 若 |S| < 格子数：补充高频填充字（如"的、了、是、在"等，增加偶然成词）

3. 字放置（核心约束求解）：
   a. 为每个目标词 w，规划一条网格上的路径 P_w（相邻、不冲突）
   b. 用回溯 + 启发式（优先放置约束最强的字，即出现在多个目标词中的字）
   c. 路径可交叉共享字（如"中"同时属于"中国"和"中华"）
   d. 放置失败则换路径或换目标词集，重试 N 次

4. 剩余空格填充：
   - 从高频字池随机选字填充
   - 填充时做"局部丰度检查"：避免某区域过度密集成词

5. 验证（BFS / DFS）：
   - 对 W 中每个词，在网格上搜索是否存在合法路径
   - 同时统计网格中可形成的所有合法词数（"潜在词池"），用于难度校准

6. 输出：
   - grid[][]（汉字矩阵）
   - target_words[]（目标词集，服务端持有，用于计分时确认"稀有度"）
   - potential_count（潜在词总数，用于难度评分）
```

#### 3.2.3 难度参数映射

| 难度档 | 网格 | 目标词数 | 成语占比 | 潜在词池 | 时间 |
|---|---|---|---|---|---|
| 入门 | 4×4 | 5-7 | 10% | 15-25 | 3 min |
| 标准 | 5×5 | 8-12 | 25% | 30-50 | 3 min |
| 高难 | 6×6 | 14-20 | 40% | 60-100 | 3 min |

> 潜在词池 = 网格中所有可形成的合法词。普通玩家一局能找到其中的 20%-40%，高手可达 60%+。

### 3.3 防作弊

| 环节 | 措施 |
|---|---|
| 网格 | 服务端生成，下发仅含汉字矩阵，不下发目标词列表 |
| 提词校验 | 玩家提交词 → 服务端查词库 + 校验路径合法性 → 返回是否有效 + 稀有度 |
| 计分 | 服务端计算，客户端仅显示 |
| 对战同步 | 服务端权威，客户端只发"操作意图" |
| 异常检测 | 单局找到词数远超潜在词池、反应时间异常短 → 标记复核 |

## 4. 游戏模式

### 4.1 单人闯关模式

#### 4.1.1 结构

- **章节制**：每章 10-15 关，章末有 Boss 关
- **主题**：每章一个文化主题（见 §4.1.4）
- **进度**：线性解锁，达到目标即可进入下一关
- **三星评价**：每关按完成度给 1-3 星，集星解锁章节

#### 4.1.2 关卡目标类型

| 类型 | 示例目标 | 设计意图 |
|---|---|---|
| 分数关 | "得到 120 分" | 基础积累 |
| 词数关 | "找到 8 个词" | 鼓励广度 |
| 成语关 | "找到 2 个成语" | 引导稀有词 |
| 限时关 | "90 秒内得到 80 分" | 紧张感 |
| 指定词关 | "找到包含'春'的词 3 个" | 训练观察力 |
| Boss 关 | "在限时内分数超过 AI 对手" | 综合检验 |

#### 4.1.3 道具系统

| 道具 | 效果 | 获取 |
|---|---|---|
| 提示 | 高亮一个目标词的首字位置 | 金币购买 / 成就 |
| 重排 | 重新生成当前网格（保留已得分） | 金币购买 |
| 冻结 | 暂停计时 10 秒 | 钻石购买 |
| 双倍 | 下一个词得分 ×2 | 看广告获得 |
| 透视 | 显示 3 秒所有目标词位置 | 钻石购买（限 Boss 关） |

每关道具使用次数有限（如最多 2 次），避免破坏平衡。

#### 4.1.4 主题章节（示例）

| 章节 | 主题 | 词库侧重 |
|---|---|---|
| 第 1 章 | 初识字海 | 高频 2-3 字词 |
| 第 2 章 | 春夏秋冬 | 季节、景物成语 |
| 第 3 章 | 诗词雅韵 | 古诗名句中的词 |
| 第 4 章 | 节气节日 | 传统节日相关词 |
| 第 5 章 | 历史典故 | 典故成语 |
| 第 6 章 | 山川地理 | 地名、地貌词 |
| 第 7 章 | 人情世故 | 情感、社交词 |
| 第 8 章 | 生僻字挑战 | 罕见字、生僻成语 |

#### 4.1.5 难度曲线

- 第 1-2 章：4×4，目标词 5-7，无时间压力
- 第 3-5 章：5×5，目标词 8-12，引入限时关
- 第 6-8 章：6×6，目标词 14+，成语占比提升，Boss 关 AI 增强

#### 4.1.6 AI 对手设计

Boss 关与匹配超时兜底均使用 AI 对手。AI 强度可调（L1-L5），核心思路：**服务端已知网格的全部潜在词池，AI 按强度参数模拟"逐词发现"过程**。

**强度档位**

| 档位 | 词汇覆盖 | 偏好 | 反应间隔 | 漏词率 | 适用 |
|---|---|---|---|---|---|
| L1 | 仅 2 字常见词 | 无偏好 | 4-6s | 50% | 第 1-2 章 Boss、新手兜底 |
| L2 | 2-3 字常见+一般 | 略偏向长词 | 3-4s | 30% | 第 3-4 章 Boss |
| L3 | 含成语 | 优先成语 | 2-3s | 15% | 第 5-6 章 Boss |
| L4 | 全词池贪心 | 优先长词+稀有 | 1.5-2s | 5% | 第 7-8 章 Boss、低段位兜底 |
| L5 | 近最优 | 严格按分值降序 | 1-1.5s | 0% | 高段位兜底、极限挑战 |

**算法**

```
输入：grid, potential_words[]（服务端已知）, level(L1-L5)

每轮决策：
1. 候选池 = potential_words 中尚未"找到"的词
2. 按 level 过滤：
   - L1：仅保留 length<=2 且 rarity=common 的词
   - L2：保留 length<=3 且 rarity in {common,normal}
   - L3+：全部保留
3. 按 level 排序偏好：
   - L1/L2：随机序
   - L3：成语优先，再按分值
   - L4/L5：严格按 (基础分×稀有度) 降序
4. 漏词判定：以 level 的漏词率概率跳过本轮（模拟"没看到"）
5. 反应延迟：在 level 的反应间隔区间内随机 sleep
6. "找到"该词 -> 按真实计分规则加分 -> 维护连击
7. 循环至时间到或候选池耗尽
```

**强度可调维度**：反应间隔、漏词率、词汇覆盖范围、排序策略四轴独立可调，便于运营微调（如活动"超强 AI 挑战周"）。

**公平性**：AI 计分与玩家同规则同公式，不享受加成；AI 找到的词不占用玩家的潜在词池（玩家仍能找到同一词，双方独立计分）。

### 4.2 多人竞赛模式

#### 4.2.1 模式总览

| 模式 | 类型 | 时长 | 说明 |
|---|---|---|---|
| 实时 1v1 | 同步 | 3 min | 双方同网格同时间，比分高低 |
| 实时 1v1v1v1（4 人混战） | 同步 | 3 min | 4 人同网格，积分排名 |
| 好友挑战 | 异步 | 不限 | 生成网格 → 分享 → 对方挑战 |
| 每日挑战 | 异步 | 3 min | 全球同一网格，当日排行 |
| 段位赛 | 同步 | 3 min | 升降段位，赛季制 |

#### 4.2.2 实时对战（核心）

- **匹配**：按段位 + 在线状态匹配，30 秒内未匹配到则匹配 AI（段位相近）
- **网格同步**：双方收到同一网格（服务端生成的同一局种子）
- **过程不可见**：双方看不到对方操作（防抄），仅看实时分数条
- **得分广播**：服务端每秒推送双方当前分数 + 连击状态，制造紧迫感
- **结算**：时间到，双方分数高者胜；平局看稀有词数；再平局看连击峰值

#### 4.2.3 好友挑战（裂变关键）

- 玩家 A 完成一局后生成"挑战卡片"（含网格种子 + A 的分数）
- 分享到微信好友/群，好友 B 点击进入小程序直接挑战同一网格
- B 完成后双方都能看到对比，B 可继续向 C 发起挑战
- **裂变钩子**：B 首次挑战成功送 A 和 B 各 1 次抽奖机会

#### 4.2.4 每日挑战

- 每天凌晨刷新一张全球统一网格（5×5 标准）
- 限时 3 分钟，当日每人可挑战 3 次，取最高分
- 当晚 24:00 结算排行，Top 100 发奖励（金币 + 称号）
- 类似 "Wordle" 的社交讨论效应：每天大家都在聊"今天的词好难找"

#### 4.2.5 段位赛（赛季制）

| 段位 | 名称 | 升降规则 |
|---|---|---|
| 1 | 字童 | 起始段位 |
| 2 | 字生 | 胜场积累 |
| 3 | 字秀 | 净胜 5 场 |
| 4 | 字举 | 净胜 10 场 |
| 5 | 字士 | 净胜 20 场 + 胜率 55% |
| 6 | 字翰 | Top 10% 玩家 |
| 7 | 字圣 | Top 1% 玩家 |

赛季每 4 周一届，赛季末按段位发奖励（皮肤、称号、钻石），段位部分重置。

## 5. 成长与经济系统

### 5.1 玩家成长线

```
段位（竞技）  ／
              ｜—— 综合玩家"等级"
通关进度（PvE）＼
              
词库图鉴（收集）—— 文化成就感
成就/称号—— 社交炫耀
```

## 7. 技术架构（多端跨平台）

> 多端扩展（微信/支付宝/抖音/百度/QQ/快手小程序 + 快应用 + H5 + Android/iOS）是硬需求，架构从一开始就按"跨端前端 + 独立后端"设计，不绑定单一小程序平台。

### 7.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | **uni-app x**（Vue 3 + TypeScript + UTS） | 一套代码编译到全部目标端（含快应用）；UTS 编译为原生，性能接近原生，规避传统跨端框架运行时开销 |
| 状态管理 | Pinia | Vue 3 官方推荐，TS 友好 |
| 构建工具 | Vite | uni-app x 默认，HMR 快 |
| UI 组件 | 自绘网格 + uni-ui 基础组件 | 网格/连线需高度定制，自绘视图层 |
| 后端框架 | **Nest.js**（Node.js + TypeScript） | 与前端同语言，TS 全栈；模块化、依赖注入适合中大型服务 |
| 主数据库 | **PostgreSQL** | 关系型，事务强；JSONB 存灵活字段；GIN 索引可辅助词库检索 |
| 缓存/实时 | **Redis** | 对局状态、排行榜（ZSET）、限流、会话、连击计时 |
| 实时通信 | **WebSocket**（socket.io） | 实时对战双向推送；socket.io 自带重连/房间 |
| 网格生成服务 | **Go** 独立微服务 | 回溯算法计算密集，Go 并发+性能优；Node 通过 gRPC/HTTP 调用 |
| 对象存储 | 阿里云 OSS / 腾讯云 COS | 词库文件、皮肤资源、分享图 |
| CDN | 云厂商 CDN | 静态资源加速 |
| 部署 | Docker + 云服务器（ECS）+ Nginx | 容器化，便于弹性扩缩 |
| 监控 | Sentry + Prometheus + Grafana | 错误追踪 + 指标监控 |
| CI/CD | GitHub Actions / GitLab CI | 自动构建发布各端 |

**关键技术决策说明**

- **为何不用微信云开发**：多端需求下，支付宝/抖音/快应用无法使用微信云开发，必须独立后端。独立后端也避免供应商锁定。
- **为何选 uni-app x 而非 Taro**：uni-app x 编译为原生代码（UTS），连线滑动的触摸性能更接近原生；快应用支持更成熟。Taro（React）为备选，若团队偏 React 可切换，业务层无侵入。
- **为何网格生成用 Go**：回溯+约束求解是 CPU 密集任务，Go 的 goroutine 并发预生成 + 性能远优于 Node；独立服务便于独立扩缩容。

### 7.4 关键数据模型（PostgreSQL）

> 由云数据库集合改为关系型表。以下为核心表结构。

#### 7.4.1 `users` 用户

```sql
CREATE TABLE users (
  id            BIGSERIAL PRIMARY KEY,
  phone         VARCHAR(20) UNIQUE,          -- 跨端账号合并主键
  nickname      VARCHAR(64),
  avatar        TEXT,
  level         INT DEFAULT 1,
  exp           INT DEFAULT 0,
  rank_tier     SMALLINT DEFAULT 1,
  rank_score    INT DEFAULT 0,
  coins         INT DEFAULT 0,
  diamonds      INT DEFAULT 0,
  stamina       INT DEFAULT 5,
  stamina_updated_at TIMESTAMPTZ DEFAULT now(),
  chapter_current INT DEFAULT 1,
  found_words   JSONB DEFAULT '[]',          -- 图鉴词数组
  achievements  JSONB DEFAULT '[]',
  skins         JSONB DEFAULT '["default"]',
  created_at    TIMESTAMPTZ DEFAULT now()
);
```

#### 7.4.2 `user_auths` 多端账号绑定（一对多）

```sql
CREATE TABLE user_auths (
  id         BIGSERIAL PRIMARY KEY,
  user_id    BIGINT REFERENCES users(id),
  platform   VARCHAR(32) NOT NULL,   -- wechat_mp/alipay_mp/douyin_mp/quickapp/h5/android/ios
  openid     VARCHAR(128) NOT NULL,  -- 平台内唯一
  unionid    VARCHAR(128),           -- 微信开放平台 unionid（可选）
  UNIQUE(platform, openid)
);
```

> 跨端账号合并：同手机号视为同一用户；微信开放平台 unionid 跨微信系产品合并。

#### 7.4.3 `matches` 对局

```sql
CREATE TABLE matches (
  id            UUID PRIMARY KEY,
  type          VARCHAR(16) NOT NULL,   -- pvp_1v1/pvp_4p/daily/friend
  grid_seed     VARCHAR(64) NOT NULL,
  grid          JSONB NOT NULL,
  target_words  JSONB NOT NULL,         -- 服务端持有
  status        VARCHAR(16) DEFAULT 'ongoing',
  winner_id     BIGINT,
  started_at    TIMESTAMPTZ DEFAULT now(),
  ended_at      TIMESTAMPTZ
);
-- 对局玩家分数实时存 Redis，结束后落库 match_players 表
```

#### 7.4.4 `daily_challenges` / `leaderboards`

- 每日挑战：每日一条记录（date + grid + target_words）
- 排行榜：Redis ZSET 实时排序，定时落库 `leaderboard_snapshots` 归档

#### 7.4.5 `dictionary` 词库

```sql
CREATE TABLE dictionary (
  word       VARCHAR(16) PRIMARY KEY,
  length     SMALLINT NOT NULL,
  frequency  REAL NOT NULL,
  rarity     VARCHAR(8) NOT NULL,   -- common/normal/rare/idiom
  tags       JSONB DEFAULT '[]',
  chars      JSONB NOT NULL,        -- 拆字数组
  meaning    TEXT
);
CREATE INDEX idx_dict_chars ON dictionary USING GIN (chars);
CREATE INDEX idx_dict_rarity ON dictionary (rarity);
CREATE INDEX idx_dict_length ON dictionary (length);
```

### 7.5 统一账号体系

多端登录流程：

```
客户端(某端) -> 平台 login SDK 取 code
            -> 后端 /auth/login {platform, code}
后端：
  1. 用 code 向平台换 openid（平台间 API 不同，由 platform adapter 处理）
  2. 查 user_auths(platform, openid)
     - 已存在 -> 取 user_id，签发 JWT
     - 不存在 -> 若有手机号授权则按手机号合并；否则新建 user + user_auths
  3. 返回 JWT（内部 uid）
```

- 内部所有业务用 `user_id`（JWT），不感知平台
- 支付聚合层：按当前端 platform 路由到对应支付 SDK
- 分享：好友挑战用**通用深链**（含 grid_seed），各端落地页解析深链进入对应网格

### 7.6 词库与网格生成服务（Go）

独立 Go 微服务，职责：

1. **词库索引加载**：启动时从 PostgreSQL 加载词库到内存，建 Trie + chars 倒排索引
2. **网格生成**：实现 §3.2.2 算法，goroutine 并发预生成
3. **潜在词池计算**：对给定网格 DFS 枚举所有合法词（用于难度校准 + AI 决策）
4. **提词校验**：Nest.js 转发提词请求，Go 服务校验"词在词库 + 路径在网格合法"

```
grid_pool（Redis + PG 持久化）：
  key = difficulty_level
  val = [grid_id, grid_id, ...]  预生成待用网格
定时任务每 10 分钟补充各档库存至阈值
```

### 7.7 实时对战架构

```
玩家 A ─┐                     ┌─ 玩家 B
        ├─ WebSocket 房间 ────┤
        └─ Nest.js 实时网关 ───┘
              │
          Redis（房间状态/分数/计时）

流程：
1. 匹配：玩家进入匹配队列（Redis），按段位配对；超时配 AI
2. 开局：从 grid_pool 取同网格，下发双方；创建 WS 房间
3. 对局：玩家提交词 -> Nest 校验计分 -> 写 Redis -> 广播双方分数/连击（增量推送）
4. 结束：计时到 -> 定胜负 -> 落库 -> 推送结算
断线：30s 内重连恢复；超时则 AI 接管或判负
```

### 7.8 性能考量

| 场景 | 风险 | 应对 |
|---|---|---|
| 连线滑动卡顿 | 触摸事件高频 | uni-app x 用 UTS 渲染层处理触摸，避免逻辑层通信延迟；网格用原生视图 |
| 网格生成慢 | 回溯算法耗时 | Go 预生成网格池，对局直接取用 |
| 实时对战延迟 | WS 推送 | socket.io 房间 + 心跳；分数增量推送；Redis 内存读写 |
| 词库查询 | 2 万+ 条 | Go 内存 Trie，O(词长) 查询；PG GIN 索引兜底 |
| 多端包体积 | 资源过大 | 词库不全量打包，按需下载；皮肤资源 CDN |

### 7.9 部署架构

```
                    ┌── CDN（静态资源/皮肤）
                    │
客户端(各端) ──Nginx── 业务 ECS 集群（Nest.js，多实例）
                    │      │
                    │      ├── PostgreSQL（主从）
                    │      ├── Redis（主从/哨兵）
                    │      └── Go 网格服务（独立 ECS）

                    └── OSS/COS（资源存储）

CI/CD：推送 -> 构建 uni-app x 各端产物 + Docker 镜像 -> 发布
```
