## 1. 概述

### 1.1 目标
打通社交裂变闭环的三件套：
1. **好友挑战（异步）**：A 玩完一局生成挑战（同网格 + 成绩），分享链接给好友 B；B 打开挑战同网格，完成后双方可见对比，B 可再分享给 C。
2. **每日挑战**：每天凌晨刷新全球统一网格（5×5 standard），每人当日 3 次机会取最高分，榜单实时可查。
3. **排行榜**：Redis ZSET 三档（每日榜 / 自然月赛季榜 / 历史最高单局总榜），Top 50 + 自己排名。

### 1.2 可运行状态（H5 双标签页验证）
- Tab A 完成一局 → 结算页「发起挑战」→ 创建挑战记录 → 复制挑战链接（H5 URL）。
- Tab B 打开链接 → 深链落地页（未登录先登录回跳）→ 显示"XXX 得分 XX，打败 TA"→ 开始挑战同一网格 3 分钟 → 提交后看对比（赢/输）。
- Tab A 回到「我的挑战」页看到 B 的成绩与胜负。
- 每日挑战页：今日统一网格、已用次数 0/3、今日最高分；同一 CST 日任意账号拉到的网格一致；第 4 次结算被拒。
- 排行榜页三 tab（每日/赛季/总榜）正确排序，底部显示我的排名。
- `npm run build:mp-weixin` 编译通过（真机分享链路线下，登记技术债，见 §11）。

### 1.3 范围
- **In**：好友挑战（create/get/start/submit/mine + 分享链接 + 深链落地页）、每日挑战（cron 统一网格 + 3 次限制 + 结算 + 金币奖励）、排行榜（Redis ZSET 三档 + Top50 + 自己排名 + 定时归档）、`challenges`/`challenge_attempts`/`daily_challenges`/`daily_attempts`/`leaderboard_snapshots` 建表、前端四个新页面 + Home 入口扩展、后端单测。
- **Out**：AI 兜底/段位/4 人混战（→ 8）、裂变抽奖钩子（GDD §4.2.3，→ 8 登记技术债）、每日 Top100 称号奖励（→ 8）、微信小程序真机分享（onShareAppMessage + 小程序码 + 场景值，→ 9）、每日"Wordle 社交讨论区"。

### 1.4 对齐 GDD

## 2. 总体架构

```
上游结算入口（统一复用 GameService.endGame）
  ├─ 自由/闯关/对战/每日/好友   ──→ 总榜 lb:all 更新（endGame 内集中）
好友挑战（ChallengeModule）
  ├─ 创建（从本人 match_session 复制网格）→ challenges
  ├─ 开始（createSessionFromRaw）→ B 的 match_session
  └─ 提交（endGame + 写 attempt + 对比）→ challenge_attempts
每日挑战（DailyModule）
  ├─ cron 每 5 分钟 ensureToday → daily_challenges（CST 对齐）
  ├─ start/submit → daily_attempts（3 次限制 + 取最高）
  └─ 结算发奖（Top100 金币 + 归档 snapshots）
排行榜（LeaderboardModule）
  ├─ ZSET：lb:daily:{yyyyMMdd} / lb:season:{yyyyMM} / lb:all
  └─ 查询 Top50 + 我的排名（users 表批量查昵称）
```

### 2.1 核心决策：所有结算统一走 `GameService.endGame`

本迭代三个新模式（好友/每日）**不做独立计分通道**，全部复用 `submitWord`（WS 提词不变）+ `endGame`（结算权威）：

- 好友挑战 start / 每日挑战 start 都只是"用指定网格建 match_session"（`createSessionFromRaw`），与闯关 startLevel、对战 setupMatch 同源。
- 提交（submitChallenge / submitDaily）内部先 `gameService.endGame(sid)` 拿权威分数与 foundWords，再写各自的 attempt/榜单逻辑。
- **总榜在 `endGame` 内集中更新**（`lb:all` ZADD max），自由/闯关/对战/每日/好友五类模式全部自动覆盖，不改各调用方。

### 2.2 模块依赖（单向，避免循环）

```
GameModule（exports GameService）──┐
DictionaryModule、AuthModule、TypeOrm ──→ ChallengeModule
GameModule、AuthModule、TypeOrm      ──→ DailyModule     （含 @Interval cron）
GameModule、AuthModule、TypeOrm      ──→ LeaderboardModule
```

- `ChallengeModule` / `DailyModule` 均 `imports: [GameModule, AuthModule, TypeOrmModule.forFeature([...])]`。GameModule 已经 exports `GameService`（供 MatchModule 使用），无需 forwardRef。
- `createSessionFromRaw` 是 `GameService` 新增方法（见 §4.2），对既有 `createSessionFromGrid` 做内部收敛，不破坏 MatchModule 调用。

### 2.3 时区约定（每日边界 + 赛季周期）

- 游戏运营边界统一 **Asia/Shanghai（UTC+8）**，不用服务器本地时区。
- 工具函数 `getCstDateStr()`（返回 `YYYY-MM-DD`）与 `getCstMonthStr()`（返回 `YYYYMM`），放 `server/src/common/time.ts`。
- 自然月作"占位赛季"（决策 #2），正式段位赛季迭代 8 替换。

## 3. 数据模型（PostgreSQL，synchronize: true）

### 3.1 `challenges`（好友挑战记录，GDD §7.4.4 风格）

```typescript
@Entity('challenges')
export class ChallengeEntity {
  @PrimaryColumn('uuid') id!: string
  @Column({ type: 'varchar', length: 64 }) gridSeed!: string     // 网格种子（原 gridUuid 或 daily-{date}）
  @Column({ type: 'jsonb' }) grid!: string[][]                  // 冗余存网格，供被挑战者创建会话
  @Column({ type: 'jsonb' }) targetWords!: string[]
  @Column({ type: 'jsonb' }) potentialWords!: string[]
  @Column({ type: 'int' }) potentialCount!: number
  @Column({ type: 'smallint' }) size!: number                   // 固定 5
  @Column({ type: 'int', default: 180 }) duration!: number      // 好友挑战 180s（决策 #5）
  @Column({ type: 'bigint' }) challengerId!: number             // 发起人
  @Column({ type: 'int' }) challengerScore!: number             // 发起时成绩
  @Column({ type: 'varchar', length: 64, nullable: true }) challengerNickname!: string | null
  @Column({ type: 'int', default: 0 }) attempts!: number        // 被挑战人次
  @Column({ type: 'int', default: 0 }) bestScore!: number       // 被挑战者最高分
  @Column({ type: 'bigint', nullable: true }) bestUserId!: number | null
  @CreateDateColumn() createdAt!: Date
}
```

## 5. 好友挑战（ChallengeModule）

### 5.1 创建（A 侧）`POST /challenge/create`

- body：`{ matchSessionId }`。
- 服务端：读 `match_session:{sid}` → 校验存在、`session.userId == req.user.userId`（防用他人会话假装）、`session.grid` 存在。
- 读取字段：`gridUuid || 'challenge-{uuid}'`（gridSeed）、`grid`、`targetWords`、`potentialWords`、`potentialCount`、`score`（发起时成绩）、`size = JSON.parse(grid).length`。
- 建 `ChallengeEntity`，`challengerNickname` 从 users 表读取。
- 返回 `{ challengeId }`。
- **来源**：自由模式/每日挑战/好友挑战的结算页点「发起挑战」都走这里（对战/闯关暂不展示入口，决策 #7）。
- **转发裂变**：B 完成某挑战后点「分享我的挑战」，用 B 自己的 match_session 再 create 一次 → 新 challenge 的 challenger=B（成绩=B 刚完成的分数），网格与来源挑战相同 → B 向 C 发起挑战自然成立（GDD §4.2.3"B 可继续向 C 发起挑战"）。

### 5.2 详情（落地页）`GET /challenge/:id`

- 校验存在；**不返回 grid**（防预习）。
- 返回：

```json
{
  "id": "uuid", "gridSeed": "gridUuid",
  "duration": 180,
  "challenger": { "userId": 1, "nickname": "玩家xxx", "score": 320 },
  "stats": { "attemptCount": 2, "bestScore": 340, "bestNickname": "玩家yyy" },
  "myBest": 340,
  "beatChallenger": true
}
```

- `myBest` / `beatChallenger` 按当前用户（若已是被挑战者）计算。

### 5.3 开始（B 侧）`POST /challenge/:id/start`

1. 校验 challenge 存在。
2. `createSessionFromRaw({ 从 challenge 三件套 }， req.user.userId, challenge.duration)`。
3. 会话 hset 附加：`challengeId`、`isChallengeMode='1'`。
4. 返回 `{ matchSessionId, grid, size, duration, challenger: { nickname, score } }`（前端顶部显示"击败目标"）。

### 5.4 提交（B 侧）`POST /challenge/:id/submit`

body `{ matchSessionId }`：

1. 读会话 → 校验 userId 归属、`session.gridUuid === challenge.gridSeed`（必须打的是同一网格）。
2. **幂等**：`challenge_attempts` 若已有 `(challenge_id, match_session_id)` → 直接返回已存结果。
3. `const result = await this.gameService.endGame(sid)`（权威结算 + 图鉴收集 + 总榜更新）。
4. 写 `ChallengeAttemptEntity`（`beat = result.score > challenge.challengerScore`）。
5. 更新 challenge：`attempts+1`；若 score > bestScore 则更新 `bestScore/bestUserId`。
6. 返回对比：

```json
{
  "saved": true, "beat": true,
  "my": { "score": 345, "maxCombo": 8, "foundCount": 12, "foundWords": [...] },
  "challenger": { "nickname": "玩家xxx", "score": 320 },
  "rank": 3
}
```

### 5.5 我的挑战 `GET /challenge/mine`

返回我发起的挑战列表（front 最新在前）：

```json
{ "challenges": [{
  "challengeId": "uuid", "createdAt": "...",
  "challengerScore": 320, "attemptCount": 3,
  "bestScore": 360, "bestNickname": "玩家yyy",
  "beaten": true
}]}
```

## 6. 每日挑战（DailyModule）

### 6.1 统一网格生成与结算（cron 惰性刷新）

`DailyService implements OnModuleInit`，`@Interval(5 * 60 * 1000)` 跑 `ensureToday()`：

```
ensureToday():
  today = cstDateStr()
  if daily_challenges 存在 today： return
  // 跨日：先结算"最近一个未 settled 的既有记录"（通常是昨天）
  pending = daily_challenges where settled=false order by date desc（排除今天）
  if pending 存在： settleDaily(pending.date)
  // 再生成今天的统一网格
  generated = generateGrid('standard', dictWords, trie)     // 复用 grid-pool 的字典加载？
  insert daily_challenges(date=today, gridSeed=`daily-{yyyyMMdd}`, 三件套+size=5, duration=180)
```

- **字典/Trie 来源**：DailyService 注入 `DictionaryService`，`onModuleInit` 时 `loadAll()` 一次（与 GridPoolService 同构；两处各自持有可接受，词库 1.5 万不大）。
- **为什么惰性**：cron 表达式与容器时区易踩坑，`@Interval` + CST 判定幂等且进程重启不丢不重。
- **月份翻转**：跨月时（进入新月份的第一天）额外 `settleSeason(上月)`：归档 `lb:season:{上月}` Top 100 到 snapshots（`season` 类型）、删除该 ZSET。**赛季榜奖励迭代 8 做**（决策 #2/#3 之赛季无奖励，单独说明）。

### 6.2 `settleDaily(dateStr)`（当晚结算发奖）

1. 从 `lb:daily:{yyyyMMdd}` ZREVRANGE 0 99 WITHSCORES 取 Top 100。
2. **发金币**（users.coins += ）：第 1 名 +500；第 2-10 名 +200；第 11-100 名 +100（决策 #3，称号奖励迭代 8）。
3. 归档：逐条 upsert `leaderboard_snapshots(type='daily', period=yyyyMMdd, rank)`（唯一约束幂等）。
4. 删除 `lb:daily:{yyyyMMdd}`（避免 Redis 膨胀；历史已归档）。
5. `daily_challenges.settled = true`。
6. **幂等**：settled 标志 + snapshot 唯一约束双重保证，重启重复触发不重复发钱。

### 6.3 API

#### `GET /daily`
```json
{ "date": "2026-08-30", "size": 5, "duration": 180,
  "attemptsUsed": 1, "attemptsLeft": 2, "myBest": 210 }
```

#### `POST /daily/start`
1. `ensureToday()` 兜底（保证记录存在）。
2. 宽松校验 `attemptsUsed < 3`（小于 3 或没玩到最后都放行，硬限制在 submit）。
3. `createSessionFromRaw(dailyCha 三件套, userId, 180)`；会话 hset 附 `dailyDate`、`isDailyMode='1'`、`gridUuid=daily-{date}`。
4. 返回 `{ matchSessionId, grid, size, duration, date, attemptsLeft }`。

#### `POST /daily/submit`  body `{ matchSessionId }`
1. 读会话 → 校验 userId 归属、`session.gridUuid === daily-{日期}`（今日统一网格）、`session.dailyDate === cstDateStr()`。
2. **3 次限制**：`COUNT(daily_attempts WHERE date=today AND user_id=user)`，≥3 → `400 ATTEMPTS_EXHAUSTED`。
3. **幂等**：同 session 已有记录 → 返回已存结果。
4. `endGame(sid)`（权威 + 图鉴 + 总榜）。
5. 写 `DailyAttemptEntity`。
6. 更新榜单（三者都是 condition-max，用 zscore 比较后 zadd，或直接取当日/当月最大一次写入）：

```json
{
  "saved": true, "score": 345, "attemptsLeft": 1, "myBest": 345,
  "maxCombo": 8, "foundCount": 12, "foundWords": [...]
}
```

> 玩家在结算页看到"本次 345 分 / 今日最佳 345 / 剩余 1 次"，与实时对战 14.4 的反馈风格一致。

## 7. 排行榜（LeaderboardModule）

### 7.1 Redis ZSET 键与指标（决策 #2）

| key | 语义 | 更新时机 |
|---|---|---|
| `lb:daily:{yyyyMMdd}` | 今日每日挑战最高分 | `POST /daily/submit`（当日所有 attempts 取 max） |
| `lb:season:{yyyyMM}` | 本月每日挑战单日最好成绩中的最高 | `POST /daily/submit`（max 合并） |
| `lb:all` | 历史最高单局得分（任意模式） | `GameService.endGame` 内集中更新 |

- member = `userId.toString()`，score = 分数。
- 有条件更新：`zscore` 读现值 → 新分更大才 `zadd`（避免低分覆盖高分）。

### 7.2 查询 `GET /leaderboard?type=daily|season|all`

```
daily  → period = cstDateStr()（yyyyMMdd）
season → period = cstMonthStr()（yyyyMM）
all    → period = 'all'
```

返回：

```json
{
  "type": "daily", "period": "20260830",
  "mine": { "userId": 5, "nickname": "玩家xxx", "score": 345, "rank": 3 },
  "list": [
    { "userId": 88, "nickname": "玩家a", "score": 500 },
    { "userId":  3, "nickname": "玩家b", "score": 430 }
  ]
}
```

- `list` = `ZREVRANGE key 0 49 WITHSCORES`（Top 50），随后对 userId 批量 `IN` 查 users 拿 nickname（一次查询）。
- `mine` = `ZREVRANK` + `ZSCORE`，无记录则 `null`，排名 `rank = zrevrank + 1`（或 null）。
- 玩家本人不在 Top 50 也要能看自己排名（迭代计划验收），前端在列表末尾单独显示自己的行。

### 7.3 数据一致性说明

- 每日/赛季榜只由 `daily/submit` 单点写入，无并发风险（同用户同秒提交两局极端场景下 zscore 条件更新是弱一致 max，可接受）。
- 总榜由 `endGame` 单点写入，同理。
- 昵称展示不做快照（nickname 变化会带到历史榜单），可接受；`leaderboard_snapshots` 归档的是 userId+score+rank，不受影响。

## 14. 需要注意的坑（对齐前几轮联调经验）

1. **userId 类型**：HTTP 侧 `JwtAuthGuard` 已统一 `Number(payload.userId)`（迭代 6 §14.5 修复），Redis ZSET member 与 PG 查询均以字符串转数字后使用，避免 `"3"` 与 `3` 混用导致排名失配。
2. **会话 TTL**：`match_session` TTL 600s。A 玩完一局后必须在 TTL 内点「发起挑战」，否则 404。前端在结算页即时创建，可接受；如超时提示"请重玩一局再发起挑战"。
3. **endGame 只应收敛一次**：挑战/每日 submit 内部调 endGame，前端 `endGame()` 分流后不再二次调 `POST /game/end`，避免 Attempt 幂等层兜住重复提交。
4. **完美提前结束**：每日/好友会话无 `matchId`，`submitWord` 的 perfect 分支照常触发 → 前端在 `res.perfect` 时调 `endGame()` → 按 mode 走 submitDaily/submitChallenge，结算逻辑要能处理"未到 180s 提前 submit"。
5. **分布式时钟**：cron 用 `@Interval` 跑在**单实例**上（当前部署即单实例）；多实例时需 `SETNX` 锁 ensureToday，本迭代登记说明即可。
6. **昵称转折**：challenge 冗余存 challengerNickname（创建时快照），排行榜用实时 nickname（不做快照，可接受）。
7. **front 路径**：新页面在 `pages/` 下，相对导入 core 为 `../../core/...`、api 为 `../../api`；组件内保持 `../core/...` 一级相对路径，禁止 `@/` 别名。
