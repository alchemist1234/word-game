# 《字海寻词》迭代开发计划

> 版本：v1.0
> 配套文档：《游戏设计文档.md》（GDD v0.2）
> 用途：AI coding 执行蓝图，按迭代逐步开发
> 本计划细化并取代 GDD §9 的粗略路线图，技术架构以 GDD §7（多端跨平台）为准

---

## 0. 如何使用本计划（给 AI coding 的指引）

### 0.1 核心原则

1. **每个迭代结束必须是端到端可运行可玩的状态**——不是"模块写完了"，而是"能打开、能玩一局、能验证"。这是硬性门禁，不满足不进入下一迭代。
2. **纵向切片优先**：每个迭代打通一条完整用户路径（哪怕简化），而非横向铺一层模块。
3. **技术债显式登记**：早期迭代允许简化方案（本地词库、前端生成网格、假数据），但必须在「技术债」章节登记，并在后续迭代的「还债」项中明确偿还。
4. **架构对齐 GDD §7**：技术栈为 uni-app x + Nest.js + PostgreSQL + Redis + Go 网格服务。不要引入架构外的技术选型。
5. **类型安全**：全栈 TypeScript（前端 UTS、后端 Nest.js），禁止 `any`/`@ts-ignore`。
6. **改最小集**：每个迭代只做该迭代范围内的事，不顺手重构、不扩大范围。

### 0.2 起步开发端选择

- **迭代 1-5 以 H5 为开发验证端**：uni-app x 一套代码，H5 调试最快（无需微信开发者工具、热更新即时、浏览器 DevTools 完善）。
- **同时保证微信小程序可编译通过**（CI 里跑一次编译，不要求真机调试）。
- **迭代 6（实时对战）起**：切换到微信小程序真机验证（实时对战 + 分享需要真机环境）。
- 此选择不改变最终多端目标（GDD §7.2），仅影响开发节奏。如需调整起步端，改本节即可。

### 0.3 每迭代交付物

每个迭代必须交付：
1. 可运行的代码（对应端能打开玩）
2. 该迭代的验收清单逐项通过（见各迭代「验收标准」）
3. 更新后的「技术债清单」（附录 A）
4. 简要迭代说明（改了什么、怎么验证、遗留什么）

### 0.4 AI coding 执行约定

- 按迭代编号顺序执行，不要跳迭代。
- 每个迭代内部，按「技术任务」列表顺序执行（已排好依赖序）。
- 任务里标注 `[GDD §x]` 的，去 GDD 对应章节查设计细节，不要凭空发挥。
- 遇到 GDD 未覆盖的设计分叉，按 GDD 已有风格做最小合理决策并在迭代说明里记录，不要停下来等。
- 验收标准是客观可验证的 checklist，逐条跑过。

## 迭代 1：最小可玩原型（纯前端）

**目标**：验证核心玩法交互成立——网格连线、组词判定、计分、计时、结算的完整闭环，纯前端实现。

**可运行状态**：浏览器打开 H5，看到一个 5×5 汉字网格，手指/鼠标按下首字滑动经过相邻字，松开提交；合法词加分并绿色飘字，非法词红色提示；3 分钟倒计时结束跳转结算页显示总分和找到的词列表。

**范围**：
- ✅ In：uni-app x 项目初始化、5×5 网格渲染、8 向连线触摸交互、本地词库（500 词）、前端简化网格生成（保证至少 3 个目标词可连）、本地提词校验、字数+稀有度计分、3 分钟计时、结算页
- ❌ Out：无后端、无账号、无连击、无好友/对战、不保证服务端权威、词库小

**技术任务**（按序）：
1. [S] 初始化 uni-app x 项目（Vue3 + TS），配置 H5 与微信小程序双端编译，Pinia 装好
2. [S] 建本地词库 `client/src/data/dictionary.json`（500 词，含 word/length/rarity/chars 字段，对齐 GDD §3.1.1），2 字常见词为主 + 少量成语
3. [M] 前端简化网格生成器 `client/src/core/gridGen.ts`：从词库随机选 3-5 个词，把字放到网格相邻位置（保证可连），剩余格子填高频字。**不追求算法最优，保证可解即可**（技术债 #1，迭代 2 偿还）
4. [M] 网格视图组件 `GridBoard.vue`：渲染 n×n 格子，触摸/鼠标事件实现 8 向连线（按下→滑动经过相邻格→松开），已选格高亮 + 连线特效，当前已选词实时显示
5. [S] 本地提词校验 `client/src/core/wordCheck.ts`：词在本地词库 + 路径合法（相邻、不重复）才算有效
6. [S] 本地计分 `client/src/core/score.ts`：字数基础分 × 稀有度系数（对齐 GDD §2.4.1/2.4.2，本迭代先不含连击）
7. [S] 单局状态机 `client/src/store/game.ts`（Pinia）：倒计时、已找词、当前分、开始/结束
8. [S] 结算页 `ResultPage.vue`：总分 + 找到的词列表（按分值排序）
9. [S] 页面路由：首页（开始按钮）→ 对局页 → 结算页 → 再来一局

**验收标准**：
- [ ] `npm run dev:h5` 启动，浏览器打开无 console error
- [ ] 5×5 网格显示，每局网格不同且至少能找到 3 个合法词
- [ ] 触摸划线流畅，8 向相邻均能连，松开提交有即时反馈
- [ ] 合法词加分 + 绿色飘字；非法词红色描边 0.3s + 震动
- [ ] 同一词重复提交不加分但有"已找到"提示
- [ ] 3 分钟倒计时结束自动跳结算页
- [ ] 结算页显示总分 + 词列表
- [ ] `npm run build:mp-weixin` 编译微信小程序通过（不要求真机）

**技术债登记**：
- #1 网格生成是前端简化版，不保证丰度/难度校准 → 迭代 2 换 Go 服务端版
- #2 词库仅 500 词且本地内置 → 迭代 2 导入 5000 词到 PG
- #3 提词/计分在客户端，可作弊 → 迭代 2 服务端权威化
- #4 无连击系统 → 迭代 3 补

## 迭代 2：后端基建 + 词库 + 网格生成 v1

**目标**：搭建后端三件套，导入真实词库，用 Go 实现网格生成服务端权威版，前端改为从后端拉网格、提词走后端校验。

**可运行状态**：前端打开后从后端拉取一张服务端生成的 5×5 网格（保证可解），玩家连线提交后由后端校验并返回计分；网格质量明显提升（潜在词池 30-50，对齐 GDD §3.2.3 标准难度）。仍然是"单局 vs 时钟"。

**范围**：
- ✅ In：Nest.js + PostgreSQL + Redis 搭建、词库导入（5000 词）、Go 网格生成服务 v1（可解性 + 潜在词池计算）、前端接后端 API、提词/计分服务端权威
- ❌ Out：无账号、无对战、无连击、无闯关结构

**技术任务**（按序）：
1. [M] 建仓库结构：`server/`（Nest.js）、`grid-service/`（Go）、`data/`、`docker-compose.yml`（PG + Redis 本地）
2. [M] Nest.js 骨架：模块结构（auth/game/match/dictionary）、全局异常过滤器、DTO 校验管道、配置模块、PostgreSQL（TypeORM）+ Redis 连接
3. [S] `dictionary` 表建表（对齐 GDD §7.4.5），GIN 索引
4. [M] 词库导入脚本 `data/import.ts`：从公开数据源（GDD §3.1.2）整理 5000 词 CSV/JSON，计算 frequency/rarity（GDD §3.1.3），导入 PG
5. [L] Go 网格生成服务 v1（对齐 GDD §3.2.2）：
   - 启动加载词库到内存，建 Trie + chars 倒排索引
   - 实现「目标词集选取 → 字放置回溯 → 高频字填充 → BFS 验证」流程
   - 潜在词池计算（DFS 枚举网格所有合法词）
   - 暴露 gRPC/HTTP：`GenerateGrid(size, difficulty)` 返回 grid + target_words + potential_count
   - 预生成网格池（Redis，按 difficulty 分桶）
6. [S] Nest.js `GameController`：`GET /game/grid?size=5&difficulty=standard`（从池取/调 Go 服务）、`POST /game/word`（校验词在库 + 路径合法 + 返回稀有度与分值）
7. [M] 前端改造：删除本地网格生成与本地校验，改调后端 API；计分以后端返回为准；新增 API 层 `client/src/api/`
8. [S] 网格池补充定时任务（Nest.js cron 或 Go ticker，每 10 分钟补库存至阈值，对齐 GDD §7.6）

**验收标准**：
- [ ] `docker-compose up` 起 PG+Redis，`npm run start:dev` 起后端，Go 服务独立运行
- [ ] PG 中 dictionary 表有 5000 条，rarity 分布合理
- [ ] `GET /game/grid` 返回的网格经服务端验证每个目标词可连，潜在词池在 30-50（标准难度）
- [ ] `POST /game/word` 对合法词返回有效+分值，对非法词/路径错误返回无效
- [ ] 前端从后端拉网格，提词走后端，计分以后端为准
- [ ] 连续请求 10 张网格无重复、均满足可解性
- [ ] 前端无本地词库依赖，无 console error

**技术债偿还**：#1 #2 #3 偿还。
**新增技术债**：
- #5 网格生成算法 v1 只保证可解，丰度/难度校准待打磨 → 迭代 3/5 调参
- #6 词库 5000，成语占比待提升 → 迭代 4/8 扩容

## 迭代 3：完整单局 + 计分完善

**目标**：补齐连击系统、完整计分三因子、潜在词池驱动的难度校准、完整结算页，单局体验闭环。

**可运行状态**：一局完整的 3 分钟单局——找词有连击递进音效与连击系数加成，成语金色高亮，结算页展示总分/词列表/稀有度/最高连击/潜在词池覆盖率。这是后续所有模式的"单局内核"。

**范围**：
- ✅ In：连击系统（10 秒窗口）、计分三因子完整（字数×稀有度×连击）、潜在词池统计、结算页完善、音效、网格生成难度校准调参
- ❌ Out：无账号持久化、无闯关、无对战

**技术任务**（按序）：
1. [S] 后端计分补连击因子（GDD §2.4.3）：`POST /game/word` 入参加 match_session_id，服务端维护连击状态与系数，返回当前连击数
2. [M] 单局会话状态（Redis）：session 记录已找词、当前分、连击、上次找词时间、开始时间；`POST /game/word` 原子更新
3. [S] Go 服务补「潜在词池」接口：给定 grid 返回全部合法词列表 + 总数（用于结算页覆盖率展示与难度校准）
4. [M] 网格生成难度校准：按 GDD §3.2.3 三档参数（入门 4×4/标准 5×5/高难 6×6）调整目标词数与成语占比，潜在词池落入目标区间
5. [S] 前端连击 UI：连击数显示、连击系数、10 秒倒计进度条、连击递进音效
6. [S] 前端计分展示：加分飘字（含稀有度颜色，GDD §6.3）、成语金色高亮
7. [M] 结算页完善：总分、词列表（按分值降序，成语金色）、最高连击、潜在词池覆盖率（"你找到了 X/Y 个词"）、星级预估（预留，迭代 4 用）
8. [S] 音效系统：找词成功"叮"、成语"编钟和弦"、非法"低沉短音"、连击递进音阶（GDD §6.3）

**验收标准**：
- [ ] 连续 10 秒内找词连击 +1，系数正确（GDD §2.4.3 公式），超时清零
- [ ] 计分三因子乘积正确，与 GDD §2.4.4 示例一致
- [ ] 结算页显示总分、词列表、稀有度、最高连击、覆盖率
- [ ] 三档难度网格均能生成，潜在词池落入 GDD §3.2.3 区间
- [ ] 音效在 H5 正常播放
- [ ] 一局完整流程无异常

**技术债偿还**：#4 #5 部分偿还。

## 迭代 4：用户系统 + 单人闯关 v1

**目标**：接入用户系统，实现单人闯关（章节地图、关卡、目标类型、星级、进度持久化），玩家有账号、有进度。

**可运行状态**：微信登录（或 H5 手机号验证码）后进入章节地图，玩 3 章关卡（前 2 章 4×4、第 3 章 5×5），每关有目标（分数/词数/成语/限时/指定词），完成获 1-3 星，进度与图鉴持久化到后端。

**范围**：
- ✅ In：登录（单端，微信小程序 + H5 手机号）、users/user_auths 表、章节地图、关卡配置、5 种目标类型、星级评价、进度持久化、词库图鉴雏形（found_words 收集）
- ❌ Out：无道具、无 Boss 关（迭代 5）、无对战

**技术任务**（按序）：
1. [M] `users` + `user_auths` 表建表（GDD §7.4.1/7.4.2）
2. [L] 认证模块：微信小程序 `wx.login`→`code2session`、H5 手机号验证码（先 mock 短信，技术债 #7）；JWT 签发；`POST /auth/login`（对齐 GDD §7.5 流程，单端先不合并）
3. [S] 前端登录页 + JWT 存储 + 请求拦截器自动带 token
4. [M] 关卡配置 `data/levels.json`：3 章 × 10 关，每关定义 size/difficulty/objective（对齐 GDD §4.1.2 五种目标类型）/星级阈值
5. [M] 闯关 API：`GET /chapters`、`POST /level/start`（返回该关网格）、`POST /level/submit`（结算 + 星级 + 写进度）
6. [M] `user_progress` 表：记录 chapter/level/stars/unlocked；`chapter_progress` 字段对齐 GDD §7.4.1
7. [M] 前端章节地图页 `ChapterMap.vue`：章节解锁、关卡节点、星级显示、进度条
8. [S] 前端关卡目标 UI：对局页顶部显示目标与进度（如"找到 2 个成语 0/2"）
9. [S] 结算页接星级：根据目标完成度给 1-3 星，写入后端
10. [S] 图鉴雏形：每次找词 `found_words` 去重落库；图鉴页展示已收集词（本迭代只列表，分类展示迭代 8 做）

**验收标准**：
- [ ] 微信小程序能登录拿 token；H5 能手机号登录
- [ ] 章节地图显示 3 章，第 1 章解锁，通关解锁下一章
- [ ] 5 种目标类型各至少 1 关能正常判定
- [ ] 星级正确计算并持久化，重进进度不丢
- [ ] 找到的词进入图鉴，图鉴页可查
- [ ] 通关第 3 章需要 5×5 网格

**技术债偿还**：无直接偿还。
**新增技术债**：
- #7 H5 短信验证码 mock，未接真实短信网关 → 迭代 10 接
- #8 图鉴仅列表，无分类/释义 → 迭代 8 完善

## 迭代 5：划词判定优化 + Boss 关 + 6×6

**目标**：优化划词判定体验（前端本地判定消除网络延迟，后端结算校验防作弊），章末 Boss 关靠更高目标实现（不引入 AI），补齐 6×6 高难与第 4-6 章内容。

**可运行状态**：单人闯关划词即时反馈（零延迟），第 1-6 章可玩，章末 Boss 关为高目标挑战关（非 AI 对抗），6×6 高难关卡可玩。

**范围**：
- ✅ In：划词判定前端本地化（词库下发 + 本地校验 + 后端结算权威校验）、Boss 关（更高目标，非 AI）、6×6 关卡、第 4-6 章扩容、词库扩容
- ❌ Out：无 AI 对手（AI 实现挪到迭代 8，用于对战匹配兜底 + 4 人混战补位）、无真人对战（迭代 6）

**技术任务**（按序）：

## 迭代 6：实时 1v1 对战

**目标**：实现真人 WebSocket 实时 1v1 对战，这是技术难度最高的迭代。切到微信小程序真机验证。

**可运行状态**：两个玩家匹配成功后同网格同时间对战 3 分钟，双方分数实时广播，结算判胜负。匹配超时兜底 AI。

**范围**：
- ✅ In：WebSocket 网关、匹配队列、同网格下发、分数广播、断线重连、结算、超时配 AI
- ❌ Out：4 人混战（迭代 8）、好友挑战（迭代 7）、段位（迭代 8）

**技术任务**（按序）：
1. [L] WebSocket 网关（Nest.js + socket.io，对齐 GDD §7.7）：房间模型、JWT 鉴权、心跳、连接生命周期
2. [M] 匹配服务：Redis 匹配队列，按段位（本迭代先按等级）配对，30 秒超时提示未匹配（AI 兜底待迭代 8 AI 实现后回填，技术债 #9）
3. [M] 对局生命周期：创建 match 记录 → 从 grid_pool 取同网格下发给双方 → 创建 WS 房间 → 实时计分 → 结束落库
4. [M] 实时计分：玩家 `submit_word` 经校验后写 Redis，广播双方分数/连击（增量推送，每秒或每次提交）
5. [M] 断线重连：30 秒内重连恢复房间状态；超时 AI 接管或判负
6. [S] 计时器服务端权威：服务端控制开局倒计时与 3 分钟主计时，到点广播结束
7. [M] 前端对战页：匹配中动画、双分数条、对手"找到词"提示、断线重连提示、结算页（含对手对比，GDD §6.2.2）
8. [S] `matches` + `match_players` 表落库（GDD §7.4.3）

**验收标准**：
- [ ] 两个真机/模拟器能匹配成功并对战一局
- [ ] 双方网格完全相同
- [ ] 一方找词，另一方分数条 1 秒内更新
- [ ] 一方断线 30 秒内重连能恢复，超时 AI 接管
- [ ] 结算判胜负正确（平局看稀有词数→连击峰值，GDD §4.2.2）
- [ ] 匹配超时正确提示未匹配（AI 兜底为技术债 #9，迭代 8 实现）
- [ ] 微信小程序真机验证通过

**验证环境切换**：本迭代起以微信小程序真机为主要验证端。

## 迭代 7：好友挑战 + 每日挑战 + 排行榜

**目标**：社交裂变闭环——好友挑战分享卡片、每日统一网格、排行榜。

**可运行状态**：玩完一局可生成挑战卡片分享给微信好友，好友点开进小程序挑战同网格；每天有一张全球统一网格的每日挑战，3 次取最高分；排行榜（每日/赛季/总榜）可查。

**范围**：
- ✅ In：好友挑战（异步）、分享卡片、通用深链、每日挑战、排行榜（Redis ZSET）
- ❌ Out：段位赛（迭代 8）、4 人混战（迭代 8）

**技术任务**（按序）：
1. [M] 好友挑战：`POST /challenge/create` 生成 grid_seed + 挑战记录；分享卡片（含深链 + 小程序码 + 成绩）；`GET /challenge/{id}` 拉取网格；`POST /challenge/{id}/submit` 提交成绩 + 对比
2. [S] 通用深链：grid_seed 编码进分享参数，各端落地页解析（本迭代先微信，多端迭代 9 补）
3. [M] 每日挑战：定时任务每天 0 点生成统一网格写 `daily_challenges`；`GET /daily` 拉取；每人每日 3 次，取最高分
4. [L] 排行榜：Redis ZSET 存 daily/season/all_time；`GET /leaderboard?type=` 返回 Top N + 自己排名；定时任务刷新赛季
5. [S] 前端分享卡片生成（canvas 截图 + 成绩 + 小程序码）
6. [S] 前端好友挑战落地页（从分享进入直接开打）
7. [S] 前端每日挑战入口 + 排行榜页（三 tab）

**验收标准**：
- [ ] 玩完一局能生成分享卡片，好友点开能挑战同网格
- [ ] 好友挑战完成后双方能看到对比
- [ ] 每日挑战每天 0 点刷新，全球同一网格
- [ ] 每人每日 3 次限制生效，取最高分
- [ ] 排行榜三档正确排序，能看到自己排名
- [ ] 微信真机分享链路通畅
