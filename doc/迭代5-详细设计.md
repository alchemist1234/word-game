## 2. 划词判定优化（核心）

### 2.1 问题分析

当前 `submitWord` 每次划词调 `POST /game/word`（HTTP），主要瓶颈：

| 环节 | 耗时 | 原因 |
|---|---|---|
| `dictionaryService.findByWord` | ~5-15ms | **每次查 PostgreSQL**（`repo.findOne`） |
| Redis 读写（4+ 次） | ~2-4ms | hgetall + sismember + sadd + hset，各自往返 |
| HTTP 头传输 | ~5-15ms | 每次 ~200-500 字节请求/响应头 |
| 网络往返 | ~10-30ms | 不可消除 |
| **合计** | **~20-60ms** | |

`endGame` 更慢：对每个已找/未找词循环调 `findByWord`（N+M 次 PG 查询）。

### 2.2 优化方案：后端内存三招 + WebSocket 长连接

#### 招 1：词库内存索引（最大收益，~5-15ms -> ~0.01ms）

`DictionaryService` 已有 `loadAll()` 把全词库读进内存（供网格生成建 Trie），但 `findByWord` 没复用。改造：

```typescript
@Injectable()
export class DictionaryService implements OnModuleInit {
  private cache = new Map<string, DictWord>()

  async onModuleInit() {
    const { words } = await this.loadAll()
    for (const w of words) this.cache.set(w.word, w)
  }

  /** 内存查询（同步），O(1) */
  findByWord(word: string): DictWord | null {
    return this.cache.get(word) ?? null
  }

  async loadAll(): Promise<{ words: DictWord[]; trie: Trie }> { /* 不变 */ }
}
```

- `findByWord` 从 async PG 查询改为同步 Map.get
- `endGame` 的 N+M 次循环全变 O(1)
- `DictionaryModule` 改为 `OnModuleInit` 启动时加载缓存

#### 招 2：潜在词池预存 rarity（submitWord 不查词库）

`getGrid` 时会话已存 `potentialWords`（string[]）。改为存 `potentialWordsWithRarity`（`Array<{word, rarity, length}>`），submitWord 用 Set 判定 + 直接取 rarity/length 计分：

```typescript
// getGrid 时预存
const potentialWithRarity = gridEntity.potentialWords.map(w => {
  const dict = this.dictionaryService.findByWord(w)
  return { word: w, rarity: dict?.rarity ?? 'common', length: dict?.length ?? w.length }
})
await this.redis.hset(key, {
  potentialWordsWithRarity: JSON.stringify(potentialWithRarity),
  // ... 其他字段
})

// submitWord 时用内存 Set 判定，不查词库
const potentialMap = new Map(
  (JSON.parse(session.potentialWordsWithRarity)).map(p => [p.word, p])
)
const entry = potentialMap.get(word)
if (!entry) return { valid: false, reason: 'not_in_dict' }
// entry.rarity / entry.length 直接用于 calcScore
```

"词在潜在词池"是**更强的校验**--潜在词池是网格 DFS 枚举的所有合法词，隐含"在词库"+"网格上可连"。submitWord 全程不碰 PG，不碰词库索引。

#### 招 3：Redis pipeline 批量操作

当前 submitWord 有 4+ 次独立 Redis 操作。用 pipeline 批量：

```typescript
const [sismemberResult, sessionData] = await this.redis.pipeline()
  .sismember(foundKey, word)
  .hgetall(`match_session:${sid}`)
  .exec()
// 处理结果... 计算后批量写
await this.redis.pipeline()
  .sadd(foundKey, word)
  .hset(`match_session:${sid}`, { score, combo, ... })
  .expire(foundKey, SESSION_TTL)
  .exec()
```

4 次往返压成 2 次（读批 + 写批）。

#### WebSocket 长连接（省 HTTP 头开销，~5-15ms -> ~1ms）

新增 `GameGateway`（WebSocket 网关），submitWord 从 HTTP 迁移到 WebSocket 事件：

- 全局长连接（登录后建连，退出断连），跨多局复用
- 帧头仅 2-6 字节（vs HTTP 头 200-500 字节）
- 单次 submitWord 网络开销从 ~5-15ms 降到 ~1ms

### 2.3 优化效果

| 环节 | 当前 | 优化后 |
|---|---|---|
| 词库查询 | ~5-15ms（PG） | ~0.01ms（Map / 潜在词池 Set） |
| Redis 读写 | ~2-4ms（4 次往返） | ~0.5ms（pipeline 2 次） |
| 网络协议开销 | ~5-15ms（HTTP 头） | ~1ms（WebSocket 帧） |
| 路径/拼字/计分 | ~0.1ms | ~0.1ms |
| **后端处理合计** | **~10-30ms** | **~1-3ms** |
| 网络往返（同地域） | ~10-30ms | ~10-30ms |
| **玩家感知总延迟** | **~20-60ms** | **~10-35ms** |

~10-35ms 低于人眼交互延迟感知阈值（~100ms），玩家无感。无需乐观 UI 回滚，无需前端持有词库。

### 2.4 防作弊

- 前端**不持有任何词库数据**，无法枚举找答案
- submitWord 走 WebSocket（服务端权威校验：路径 + 拼字 + 潜在词池 + 计分）
- 结算 `endGame`/`submitLevel` 服务端重算（防分数篡改）
- 作弊防御与迭代 4 一致（拼字校验 + 路径校验 + 潜在词池校验）

## 3. WebSocket 网关设计

### 3.1 技术选型：ws（原生 WebSocket）

> **决策**：GDD §7 写 socket.io，实际用 **ws（@nestjs/platform-ws）**。理由：uni-app `uni.connectSocket()` 是原生 WebSocket，跨端（H5 + 小程序）天然兼容；socket.io 有自有协议层，小程序需额外 polyfill（weapp.socket.io），增加兼容成本。房间管理（迭代 6 需要）用 Map 自行实现，简单场景够用。技术债登记。

依赖新增（server）：
```
@nestjs/websockets @nestjs/platform-ws
```

### 3.2 GameGateway（`server/src/game/game.gateway.ts`）

```typescript
@WebSocketGateway({ path: '/api/game/ws', cors: true })
export class GameGateway
  implements OnGatewayConnection, OnGatewayDisconnect, OnGatewayInit {

  @WebSocketServer() server: WebSocketServer

  /** 连接时验 JWT（token 从 query 取） */
  handleConnection(client: WebSocket, ...args): void {
    const token = extractTokenFromQuery(args)
    try {
      const payload = this.jwtService.verify(token)
      // client 附带 userId（用 WeakMap 存 client -> userId）
      clientDataMap.set(client, { userId: payload.userId })
    } catch {
      client.close(4001, 'unauthorized')
    }
  }

  /** submit_word 事件（ws 用 on('message')，Nest.js @SubscribeMessage 适配） */
  @SubscribeMessage('submit_word')
  async handleSubmitWord(
    client: WebSocket,
    payload: { sid: string; word: string; cells: number[][] },
  ): Promise<SubmitWordResult> {
    const { userId } = clientDataMap.get(client) ?? {}
    if (!userId) return { valid: false, reason: 'unauthorized' }
    const cells = payload.cells.map(([row, col]) => ({ row, col }))
    return this.gameService.submitWord(payload.sid, payload.word, cells)
  }

  handleDisconnect(client: WebSocket): void {
    clientDataMap.delete(client)
  }
}
```

- JWT 鉴权：WebSocket 握手时无法设 Authorization header，token 通过 query 参数传递（`?token=xxx`）
- `client -> userId` 映射用 `WeakMap<WebSocket, { userId }>` 存（避免修改 WebSocket 实例）
- cells 压缩为 `number[][]`（`[[r,c],...]`），比 `{row,col}[]` 省字节

### 3.3 消息协议（JSON）

**客户端 -> 服务端**：
```json
{ "event": "submit_word", "data": { "sid": "uuid", "word": "中国", "cells": [[0,0],[0,1]] } }
{ "event": "ping" }
```

**服务端 -> 客户端**：
```json
{ "event": "word_result", "data": { "valid": true, "score": 5, "rarity": "common", "totalScore": 45, "combo": 2, "comboBonus": 1, "comboRemainingMs": 10000, "perfect": false } }
{ "event": "word_result", "data": { "valid": false, "reason": "duplicate" } }
{ "event": "pong" }
{ "event": "error", "data": { "message": "会话已过期" } }
```

### 3.4 心跳与重连

- **心跳**：客户端每 30s 发 `ping`，服务端即返 `pong`。60s 未收到 pong 视为断线
- **重连**：`uni.onSocketClose` 触发重连（指数退避：1s -> 2s -> 4s -> 8s -> 16s，最多 5 次）
- **断线期间**：会话状态在 Redis（TTL 600s），重连后可继续当前局；断线期间玩家的提词操作暂存前端队列，重连后补发（可选，简化版可直接丢弃断线期间的提词）

### 3.5 仍走 HTTP 的 API

WebSocket 只承担高频的 `submitWord`。低频一次请求仍走 HTTP（RESTful 清晰）：

| API | 传输 | 说明 |
|---|---|---|
| `submitWord` | **WebSocket** | 高频，需低延迟 |
| `GET /game/grid` | HTTP | 取网格（自由模式） |
| `POST /level/start` | HTTP | 开始关卡 |
| `POST /level/submit` | HTTP | 提交结算 |
| `POST /game/end` | HTTP | 自由模式结算 |
| `GET /level/chapters` | HTTP | 章节地图 |
| `GET /pokedex` | HTTP | 图鉴 |

## 4. Boss 关设计（更高目标，非 AI）

### 4.1 设计思路

Boss 关**不引入 AI 对抗**，改为**更高的目标阈值**挑战。每章第 5 关为 Boss，目标显著高于同章其他关，通关有挑战感。

Boss 关标识：levels.json 加 `"boss": true` 字段，章节地图用此字段显示特殊样式（红色高亮 / Boss 图标）。

### 4.2 关卡目标配置

Boss 关复用现有 5 种目标类型（score/wordCount/idiom/timeLimit/specificWord），不引入新类型。阈值高于普通关：

| 关 | 类型 | 目标 | 说明 |
|---|---|---|---|
| 1-5 (Boss) | specificWord | 大×3 | 4×4 找 3 个含"大"的词（原×2 提升） |
| 2-5 (Boss) | specificWord | 春×2 | 4×4 找 2 个含"春"的词（原×1 提升） |
| 3-5 (Boss) | specificWord | 花×3 | 5×5 找 3 个含"花"的词（原×2 提升） |
| 4-5 (Boss) | score | 70 | 5×5 高分挑战 |
| 5-5 (Boss) | idiom | 5 | 5×5 找 5 个成语（典故章成语多） |
| 6-5 (Boss) | score | 100 | 6×6 终极高分挑战 |

> 1-3 章第 5 关只提升目标值（不改类型），已有进度保留（levelId 不变，stars 不变）。

### 4.3 星级计算

Boss 关仍用动态星级（1星=目标×0.5，2星=目标，3星=目标×1.5），无需特殊处理。现有 `calcStars` 逻辑复用。

例：4-5 Boss score 目标 70
- 1 星：35 分
- 2 星：70 分
- 3 星：105 分

### 4.4 章节地图 Boss 关样式

- Boss 关节点：红色边框 + "Boss"标签
- 未解锁：灰色锁图标
- 已通关：星级 + 红色边框

## 8. 前端设计

### 8.1 WebSocket 客户端（`client/src/api/socket.ts` 新增）

```typescript
// 全局 WebSocket 连接管理
let socket: WebSocket | null = null
let reconnectAttempts = 0

export function connectSocket(token: string, onMessage: (msg: WsMessage) => void): void {
  socket = uni.connectSocket({
    url: `${WS_BASE}/api/game/ws?token=${token}`,
    complete: () => {},
  })
  socket.onMessage((res) => onMessage(JSON.parse(res.data)))
  socket.onClose(() => {
    // 指数退避重连
    if (reconnectAttempts < 5) {
      setTimeout(() => connectSocket(token, onMessage), 1000 * 2 ** reconnectAttempts)
      reconnectAttempts++
    }
  })
  socket.onOpen(() => { reconnectAttempts = 0 })
}

export function sendWs(event: string, data: unknown): void {
  socket?.send({ data: JSON.stringify({ event, data }) })
}
```

- 登录成功后建连（`connectSocket(token, handler)`）
- `onMessage` 分发到 store（`word_result` -> 更新分数/连击，`pong` -> 心跳）
- 心跳定时器：每 30s 发 `ping`

### 8.2 store 扩展（`client/src/store/game.ts`）

新增状态：
```typescript
const wsConnected = ref(false)  // WebSocket 连接状态
```

Actions 扩展：
- `submitSelection`：从调 HTTP `submitWord` 改为 `sendWs('submit_word', { sid, word, cells })`，结果通过 `onMessage` 异步回调更新
- `handleWordResult(result)`：新增，处理 WebSocket 返回的 `word_result`，更新 score/combo/foundWords/feedback（逻辑同现有 submitSelection 的成功/失败分支）
- `connectWs()`：登录后调，建立 WebSocket 连接 + 注册 onMessage

**关键变化**：`submitSelection` 从 async/await 变为"发送 + 异步回调"。`selectedCells` 提交后立即清空（不等响应），结果回来后更新分数。这要求 UI 在发送到结果返回期间不阻塞（玩家可继续划下一个词）。

### 8.3 api 扩展（`client/src/api/index.ts`）

- `submitWord` 函数保留（向后兼容，但 store 不再调用）
- 新增 WebSocket 相关类型：`WsMessage`、`WordResultData`

### 8.4 Game 页

- **无视觉变化**：划词交互不变，只是底层从 HTTP 变 WebSocket
- Boss 关：顶部目标显示加 "Boss" 标签（红色）
- WebSocket 断线时：顶部显示"重连中..."提示条

### 8.5 Result 页

- 无变化（结算仍走 HTTP `submitLevel`/`endGame`）

### 8.6 章节地图页

- Boss 关节点红色边框 + "Boss" 标签（根据 `boss: true` 字段）

## 12. 已决策事项（v1 定稿）

| # | 问题 | 决策 |
|---|---|---|
| 1 | 划词判定方式 | 后端判定 + WebSocket 传输 + 内存优化（不用前端判定，不泄露词库） |
| 2 | WebSocket 平台 | ws（@nestjs/platform-ws），非 socket.io，理由：uni-app 跨端原生兼容 |
| 3 | 词库查询优化 | DictionaryService 内存 Map 索引 + 潜在词池预存 rarity，submitWord 不查 PG |
| 4 | Redis 优化 | pipeline 批量读写（4 次往返压 2 次） |
| 5 | Boss 关设计 | 更高目标阈值（非 AI），复用现有 5 种目标类型，不加新类型 |
| 6 | Boss 关分布 | 每章第 5 关为 Boss，1-3 章提升已有 specificWord 目标值，4-6 章新关卡 |
| 7 | 1-3 章第 5 关改动 | 只提升目标值 + 加 boss 标记，不改类型，已有进度保留 |
| 8 | 主题词库切片 | 本迭代简化（全词库 + difficulty 控制），精确切片留迭代 8 |
| 9 | WebSocket 鉴权 | token 通过 query 参数传递（握手时无法设 header） |
| 10 | 断线重连 | 指数退避（1s->16s，最多 5 次），会话 Redis TTL 600s 保活 |
| 11 | 仍走 HTTP 的 API | 低频一次请求（getGrid/startLevel/submitLevel/endGame/chapters/pokedex）走 HTTP |
| 12 | submitWord 响应模式 | 异步回调（发送后不阻塞，结果通过 WebSocket onMessage 回调更新） |
