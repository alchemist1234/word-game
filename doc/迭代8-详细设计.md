## 1. 概述

### 1.1 目标

在迭代 6（1v1 实时）+ 迭代 7（社交裂变 + 榜单）之上，补齐 GDD 第 5 章成长循环与第 4 章段位/混战/AI 的剩余拼图：

1. **段位赛**：7 档段位 + 自然月赛季（与迭代 7 排行榜赛季同口径 `yyyyMM`，不对齐 GDD 4 周，决策 #2），赛季重置部分分数 + 奖励发放。
2. **AI 对手 L1-L5（四轴可调）**：复用服务端潜在词池，模拟逐词发现；用于 1v1 匹配超时兜底 + 4 人混战缺人补位（30 秒补齐至 4 人，按房间平均段位取档位）。
3. **4 人混战**：同网格 4 方实时计分排名，WS 房间扩至 4 人，结算按分数→稀有词数→连击峰值排序，缺人 AI 补位。
4. **经济体系**：`coins / diamonds / stamina` 三货币运转，体力定时恢复、闯关消耗、每日/对战/成就/段位为获取口。
5. **道具系统（8b）**：5 种道具抽象化（配置驱动 `allowedModes` / `maxPerLevel` / `effect`），新增/删除道具仅改配置与 effect 注册。
6. **图鉴完善（8b）**：分类展示（主题/字数/稀有度）+ 释义/典故 + 完成度称号。
7. **成就系统（8b）**：配置驱动，事件触发检测 + 奖励发放（复用经济接口）。
8. **词库 2 万（8b）**：增量导入至 2 万，成语占比 ≥35%。

## 2. 总体架构

```
GameModule (GameService.createSessionFromRaw / endGame 集中总榜)
  ↑
MatchModule ←→ AiModule (AiService.simulate，MatchService 驱动)
  ↑              ↑
DailyModule   LeaderboardModule (复用 lb:season:{yyyyMM} / lb:all)
  ↑
EconomyModule (coins/diamonds/stamina，@Interval 恢复)
  ↑
Inventory/ItemModule (道具配置 + 背包 + 效果注册表)
  ↑
PokedexModule (分组 + meaning)
AchievementModule (配置 + 事件钩子 + 奖励，经 EconomyService 入账)
DictionaryModule (loadAll 内存 Map，增量至 2 万)
```

### 2.1 核心决策

- **赛季口径**：保持 **自然月 `yyyyMM`**（与迭代 7 `lb:season` / `DailyService.settleSeason` 同键），避免双赛季键分裂。GDD 的 4 周赛季作为后续可配置项，当前通过 `SEASON_MODE='month'` 开关隔离（决策 #2）。
- **4 人房间复用 1v1 内核**：不另起计分通道；每玩家仍独立 `match_session:{sid}` + `matchId` 关联，`MatchRoom.players: Map<userId|aiId, RoomPlayer>` 扩至 4。
- **AI 为虚拟玩家**：AI 不建 `users` 行，`userId` 用负数域 `-1..-4` 占位（或 `ai:L1-xxx` 字符串，统一转数字时走独立分支），分数与真人同 Redis `match_session` 结构，避免污染 `lb:all` 与排行榜。
- **经济集中化**：所有货币变更走 `EconomyService.addCoins/addDiamonds/consumeStamina`，内置 `stamina` 恢复的惰性计算（读时补齐 + cron 兜底）。
- **道具抽象**：`data/items.json` 配置 + `ItemEffectRegistry`（`effect -> handler`），新增道具仅追加配置与注册一行，不改 Controller/Service 分支。

### 2.2 模块依赖（避免循环）

```
GameModule exports GameService
AuthModule exports JwtAuthGuard / user
EconomyModule exports EconomyService
AiModule exports AiService
MatchModule imports [GameModule, GridPoolModule, DictionaryModule, AuthModule, AiModule, EconomyModule]
DailyModule imports [GameModule, DictionaryModule]
LeaderboardModule imports [DailyModule 仅复用 time 工具，实际独立]
ItemModule imports [GameModule, AuthModule, EconomyModule]
PokedexModule imports [DictionaryModule 同前]
AchievementModule imports [EconomyModule]
```

- `MatchService` 对 `AiService` 仅单向依赖（AI 不反向依赖 Match），无需 forwardRef。已有 `GameModule ⇄ MatchModule` forwardRef 保持不变。

## 4. 段位赛（8a，核心）

### 4.1 段位定义（GDD §4.2.5）

| 段位 | 名称 | 升降规则（首版简化） |
|---|---|---|
| 1 | 字童 | 起始 |
| 2 | 字生 | rankScore ≥ 100 |
| 3 | 字秀 | ≥ 300 且净胜 5 场（胜场-负场） |
| 4 | 字举 | ≥ 600 且净胜 10 场 |
| 5 | 字士 | ≥ 1000 且胜率 55%（近 20 场） |
| 6 | 字翰 | 月榜 Top 10%（赛季结算时晋升） |
| 7 | 字圣 | 月榜 Top 1% |

> 首版实现：仅用 `rankScore` 阈值 + 胜场阈值均可验证；6/7 的百分比晋升在 `settleSeason` 时批量计算。

### 4.2 分数规则

- 段位赛即 1v1/4 人对战的 **排位分变体**：`GET /match/queue?mode=ranked` 或 `POST /match/queue` body `{ mode:'ranked' }` 入排位队列（与普通 `casual` 隔离）。
- 胜：`+20 + (对手段位-己方段位)*2`（保底 +10），负：`-10 + (对手段位-己方段位)`（保底 -15），平：`±5`。
- `rankScore` 不设负下限，`rankTier` 由 `rankScore` 阈值重算（`recalcTier(score)` 纯函数）。

### 4.3 赛季周期（自然月，决策 #2）

- 键：`lb:season:{yyyyMM}`（与迭代 7 完全同键），`DailyService.intervalEnsure` 已在每月 1 日触发 `settleSeason(prevMonth)` 归档 + 删 ZSET。
- 8a 新增 `SeasonService.settleRankSeason(monthStr)`：在 `settleSeason` 之后对全量 users 按 `rankScore` 排序发放赛季奖励（金币/钻石）并做 **部分重置**：`rankScore = floor(rankScore * 0.6)`（保留 60%），重算 `rankTier`。
- 奖励档（首版金币/钻石，称号/皮肤留 10）：字圣 +500 钻石/字翰 +200 钻石/字士 +100 钻石/其余参与奖 +200 金币。

### 4.4 API

```
GET  /rank/me              → { rankTier, rankScore, wins, losses, winRate, season: yyyyMM }
GET  /rank/leaderboard?season=yyyyMM  → 复用 GET /leaderboard?type=season，新增 rankTier 透出
POST /match/queue  body { mode?: 'casual'|'ranked', size?: 1|4 } // 兼容既有无参调用
```

## 5. AI 对手（8a，核心）

### 5.1 L1-L5 配置（GDD §4.1.6 四轴）

| 档位 | 覆盖 | 排序偏好 | 反应间隔 | 漏词率 | 适用 |
|---|---|---|---|---|---|
| L1 | 仅 2 字 common | 随机 | 4000-6000ms | 50% | 1-2 章 Boss / 新手兜底 |
| L2 | 2-3 字 common/normal | 略偏长词 | 3000-4000ms | 30% | 3-4 章 Boss |
| L3 | 含 idiom | 成语优先 | 2000-3000ms | 15% | 5-6 章 Boss |
| L4 | 全池贪心 | 长词+稀有优先 | 1500-2000ms | 5% | 低段位兜底 |
| L5 | 近最优 | 分值降序严格 | 1000-1500ms | 0% | 高段位兜底/极限挑战 |

配置落地 `server/data/ai-levels.json`，`AiService` 启动时加载。

### 5.2 算法（服务端逐词模拟）

```
输入：grid + potentialWithRarity[]（已按分值预排） + level

candidatePool = 过滤 potential（按 level 覆盖）→ 按 level 排序偏好
while 未结束 and candidatePool 非空：
  if Math.random() < missRate(level): continue // 漏词
  sleep(random(interval[level]))
  pick = candidatePool.shift()
  // 计分与连击同玩家规则：calcScore(length,rarity)+calcComboBonus(combo)，维护 aiCombo/lastWordAt/maxCombo
  score += calc(...)
  broadcastScores() // 同玩家分数广播同一通道
```

- AI 不校验路径（潜在词池即合法），不占用玩家词池（独立计分）。
- AI 会话同样 `match_session:{aiSid}`，但标记 `isAi=1`，`endGame` 时跳过图鉴与 `lb:all`。

### 5.3 集成点

- **1v1 超时兜底**：`MatchService.tryPairQueue` 扫描到单人等待 >30s 时，不标记 `timeout`，而是 `setupMatchWithAi(userId)`（取网格 + 真人 sid + AI sid + 房间 2 人含 1 AI）。
- **4 人补位**：见 §6.3。
- **服务**：`AiModule` 提供 `createAiPlayer(room, level)` 与 `driveAi(room, aiId)`（定时器驱动逐词）。

## 6. 4 人混战（8a，核心）

### 6.1 房间模型扩展

```typescript
interface MatchRoom {
  matchId: string
  type: 'pvp_1v1' | 'pvp_4p'
  grid: string[][]
  size: number
  duration: number // 180
  players: Map<number, RoomPlayer> // 2 或 4（含 AI 负数 id）
  status: 'countdown' | 'playing' | 'finished'
  remainingSec: number
  ticker?: NodeJS.Timeout
  lastScores: Map<number, number>
  lastMatchEnd?: unknown
  aiTimers: Map<number, NodeJS.Timeout> // AI 驱动定时器，便于清理
}
interface RoomPlayer { sid: string; clientConnected: boolean; disconnectTimer?: NodeJS.Timeout; isAi: boolean; aiLevel?: string }
```

- `MatchEntity.type='pvp_4p'`，`MatchPlayerEntity` 4 行（含 AI 行 `isAi=true`）。
- `playerMatch: Map<number, string>` 仍为真人定位；AI 不入此 Map。

### 6.2 匹配队列

- 新增键 `match_queue_4p:{tier}` + `match_queue_4p_meta:{userId}`，与 1v1 隔离。
- `POST /match/queue` 新增 `size` 参数：`size=4` 入 4p 队列，否则 1v1。
- 轮询 `GET /match/queue?size=4` 返回 `queued/matched/timeout`，`matched` 时 `queueStatus` 同步返回 4p 开局数据（复用迭代 6 的补发 `match_join` 机制）。

### 6.3 AI 补位规则（决策 #3）

`@Interval(1000) scanQueues4p()`：

```
每 tier：若队列人数 ≥4 → 取 4 人 setupMatch4p([4 真人])
若 1≤人数≤3 且最长等待 >30s → 取全部真人 + 补 (4-真人数) 个 AI 补位
  AI 档位 = avgRankTier(真人) 映射：1-2→L2, 3→L3, 4→L4, 5+→L5，单人时按该玩家 tier
  setupMatch4p(真人 + AI占位)
```

### 6.4 对局生命周期（同 1v1，扩展为 N 方）

- `setupMatch4p`：`gridPool.acquire('standard')` 同网格 → 为每玩家（真人+AI）各 `createSessionFromGrid` → 建 `matches` + `rooms` + `playerMatch`（仅真人）→ 向**所有真人**广播 `match_start`（含 4 方对手列表）→ 3s 倒计时 → `playing` → 启动 tick + 为每个 AI 启动 `driveAi` 定时链。
- `tick`：每秒读全部 sid 的分数/combo（pipeline N 条 hgetall），广播 `match_tick_4p`（或复用 `match_tick` 但扩展为数组，见 §13）。
- `broadcastScore`：任一真人 `submit_word` 后即时广播（同 1v1 的 `broadcastScore`，改为 N 方）。
- `finishMatch4p`：对全部 sid `endGame`（AI 会话用轻量 settle，不写图鉴）→ `decideRank4p(stats[])` 按 score→rare→maxCombo 排序得 rank（同分同 rank 顺延）→ 落库 `matches` + N 行 `match_players` → 向每真人发 `match_end_4p`（含全榜单与个人 `rank/won`）。

### 6.5 断线与离开

- 复用 30s 宽限：4 人中一人断线不影响他人；超时该位判末位（分数保留，但排名强制垫底，`forfeit` 标记）。
- `POST /match/abandon` 在 4 人中视为单人弃赛（该位判负，其余按分排名）。

// EconomyService
async getStamina(userId): Promise<{ stamina, max:5, nextRecoverAt }>

  // refill = min(max - stamina, elapsedHours)，若 refill>0 则 update users.stamina+refill & staminaUpdatedAt+=refill*3600000

## 8. 道具系统（8b，抽象可配置）

### 8.1 设计目标

- 5 种效果可增删：新增道具仅改 `data/items.json` + 注册一行 effect handler。
- `allowedModes` 决定道具在哪些模式可用（每日禁重排等差异），非法模式返回 `400 ITEM_NOT_ALLOWED_IN_MODE`。
- 每关限次：`maxPerLevel` + Redis `item_usage:{sid}:{itemId}` 计数。

### 8.2 效果表（GDD §4.1.3 + allowedModes 细化）

| id | 效果 | allowedModes | 特殊限制 |
|---|---|---|---|
| hint | 高亮一个未找目标词首字 | level | — |
| shuffle | 重生同难度新网格，保留已得分 | level, pvp_1v1, pvp_4p, friend | **daily 禁用**（同网格公平性） |
| freeze | 暂停计时 10s（仅本地倒计时与服务端 remaining freeze） | level | — |
| double | 下一词 ×2 | level, friend, pvp_1v1, pvp_4p | — |
| peek | 显示 3s 全部目标词位置 | level | `bossOnly:true` 时仅 Boss 关 |

### 8.3 模型与接口

```
GET  /items                 → 返回 items.json（过滤 allowedModes 后的可用列表，前端展示）
GET  /inventory             → { items: [{itemId, quantity}] }
POST /item/use  body { matchSessionId, itemId }
  1. 校验 sid 归属 + isLevelMode/dailyMode/challengeMode/matchId 判定 mode
  2. 查 items.json 得 allowedModes/maxPerLevel/effect → 模式不允许 400
  3. Redis 计数 `INCR item_usage:{sid}:{itemId}`，超限 400 ITEM_LIMIT
  4. 查背包 quantity，不足则按 costType 扣 coins/diamonds（经 EconomyService），不足 400
  5. 调 ItemEffectRegistry.get(effect).apply(sid, params)：hint→返回 {hintCell}，shuffle→刷网格并重写 match_session.grid/potential，freeze→服务端 freezeUntil 标记，double→打标 nextDouble=1，peek→返回全部目标词坐标
  6. 扣减背包或货币，写使用计数
  7. 返回 effectResult（前端据此做高亮/重渲染/冻结倒计时/飘字）
```

`ItemEffectRegistry`：`Map<string, (sid, params, redis)=>Promise<EffectResult>>`，5 个 handler 各一文件，新增道具仅 `registry.set('newEffect', handler)`。

### 8.4 与对局/结算交互

- `double`：`submitWord` 检测 `session.nextDouble==='1'` 时 `score*=2` 并清标记。
- `freeze`：`tick` 检测 `session.freezeUntil > now` 时不递减 `remainingSec`。
- `shuffle`：重写 `session.grid/targetWords/potential*` 并清 `found` set（保留 score）。

## 18. 需要注意的坑（对齐前几轮联调经验）

1. **userId 类型**：HTTP `JwtAuthGuard` 与 WS 已统一 `Number(payload.userId)`，但 AI 负数 id 分支需显式隔离（`if userId < 0 → ai logic`），避免 `isCurrentClient` 误判。
2. **赛季双写**：`DailyService.settleSeason` 与 `SeasonService.settleRankSeason` 同月触发时注意幂等（snapshot 唯一约束 `type/period/userId`，重复触发不重复发奖）。
3. **体力惰性**：`getStamina` 必须先补齐再扣减；`consumeStamina` 与 `cronRefill` 并发时以后者幂等覆盖为准（单实例可接受，多实例需 `SETNX`）。
4. **道具并发**：`item_usage:{sid}:{itemId}` 必须 `WATCH` 或 `INCR` 原子校验超限，避免两端同时 `INCR` 绕过 `maxPerLevel`。
5. **4 人 pipeline**：N=4 时 `pipeline hgetall ×4` 需逐条取值（`results[0..3]`），勿沿用 1v1 的 2 条假设（迭代 6 §14.2 教训）。
6. **AI 计时清理**：房间结束时清理所有 `aiTimers` + `room.ticker`，否则 AI 仍对已删房间 `broadcastScores`。
7. **每日禁重排**：`shuffle` 在 `dailyMode` 必须硬拦截（GDD 公平性），前端也需按 `GET /items` 过滤隐藏该按钮，双重保障。
